## 1. 什么是事件循环（Event Loop）？ 🔄

**事件循环**是 **JavaScript 异步执行机制** 的核心，它是一种不断循环的机制，用于检查任务队列（Task Queues）中是否有待执行的任务，并将这些任务推到 JavaScript 主线程的执行栈（Call Stack）中执行。

- **核心作用：** 确保 JavaScript 这个**单线程**语言在执行耗时操作（如网络请求、计时器、用户交互）时，不会阻塞主线程，从而保持用户界面的流畅和响应性。
    
- **构成要素：** 事件循环主要涉及 **主线程/执行栈**、**Web API**、**宏任务队列**（Macrotasks Queue）、**微任务队列**（Microtasks Queue）以及循环本身。
    

**总结来说，事件循环就像一个协调者**：当 JS 引擎遇到异步 Web API 调用（如 `setTimeout`、`fetch`、DOM 事件）时，它会将这些任务交给浏览器其他线程（Web API）去处理。当异步操作完成时，Web API 会将对应的**回调函数**放入任务队列中。事件循环则负责不断地将队列中的任务取出来，放入执行栈中，让主线程执行。

## 💡 事件循环概念与内容详解

事件循环是 **JavaScript 异步机制** 的核心，确保了非阻塞 I/O 和高效的用户界面响应。尽管 JavaScript 在浏览器中是**单线程**执行的，但通过事件循环机制，它可以处理异步操作，例如计时器、网络请求和用户交互。

下面是对您提供的图片内容的详细整理和讲解：

### 一、Web API 如何与事件循环协同？

**Web API** 是浏览器环境提供的一组接口，它们**不属于** JavaScript 引擎（如 V8）的内部。这些 API 负责处理 JavaScript 引擎无法单独完成的异步操作，例如：

- **计时器（Timers）：** `setTimeout` / `setInterval`
    
    - **职责：** 由**渲染进程**内的**定时器线程**负责计时。
        
- **网络请求（Networking）：** `fetch` / `XMLHttpRequest`
    
    - **职责：** 由浏览器独立的**网络线程**负责请求和接收数据。
        
- **DOM 事件监听（DOM Events）：** `click`, `scroll` 等
    
    - **职责：** 涉及到**操作系统事件**和浏览器的**渲染进程**。
        

它们的共同特点是：它们都由浏览器的**不同进程/线程**具体负责执行异步任务，当任务完成（如计时结束、数据返回、事件触发）时，它们会将对应的 **回调函数** 包装成一个任务（宏任务或微任务）放入相应的任务队列中，等待事件循环来调度执行。

### 二、事件循环的完整一轮流程（共 6 步）

事件循环的每一轮都旨在保持主线程的繁忙，并确保 UI 的响应性。其核心步骤是：

#### Step 1: 取出一个宏任务 📜

事件循环的每一轮，都会从**宏任务队列**（Macrotask Queue，也常被称为 Task Queue 或 Callback Queue）中取出**最老**的一个任务来执行。

**常见的宏任务来源：**

- 页面的 `<script>` 标签执行（整个初始代码块本身就是一个宏任务）。
    
- `setTimeout` / `setInterval` **到期后的回调函数**。
    
- DOM 事件回调（如 `click`、`scroll` 等）。
    
- 网络请求完成后的回调（如 `fetch`、`XHR` 的响应回调）。
    

#### Step 2: 执行宏任务中的 JS 代码 💻

执行取出的宏任务中的 JavaScript 代码。在这个执行过程中，可能会发生以下情况：

- **创建新的微任务：** 例如 `Promise.then()` 回调、`await` 后续代码、`MutationObserver` 回调等，这些新的微任务会被立即添加到 **微任务队列** 中。
    
- **安排未来的宏任务：** 例如再次调用 `setTimeout` / `setInterval` 或继续注册事件监听器。
    

#### Step 3: 清空微任务队列 🧹

**宏任务执行结束后**（即 JavaScript 执行栈清空后），事件循环会**立即**开始处理所有排队的 **微任务**（Microtasks）。

- **“清空”过程：** 微任务会**持续执行**，直到微任务队列完全清空。如果在执行微任务的过程中，又产生了新的微任务，它们也会被添加到队列尾部并**在当前这一轮**全部执行完毕。
    
- **优先级：** 微任务的优先级**高于**下一个宏任务和渲染。这意味着微任务可以阻塞渲染和用户输入，因此需要谨慎使用。
    

#### Step 4: 是否进行渲染更新？ 🖼️

微任务队列清空后，浏览器会进行判断：

1. **当前是否到了下一次屏幕刷新时机？** (由显示器的 **V-Sync** 信号和帧率决定，通常是 60Hz，即大约每 16.6ms 一次)。
    
2. **当前页面是否有“渲染需求”？** (例如 DOM 结构或样式发生了变更)。
    

如果满足上述条件，浏览器将进行渲染更新（即“绘制一帧”）：

1. **处理事件回调：** 处理 `scroll`、`resize` 等事件回调。
    
2. **执行 `requestAnimationFrame` 回调：** 这是一个专门用于高性能动画的回调，它会在渲染前被执行。
    
3. **执行样式计算 (Style) 与布局 (Layout)：** 计算元素的最终样式和在屏幕上的位置。
    
4. **执行 Observer 回调：** 例如 `ResizeObserver`、`IntersectionObserver` 等。
    
    - **注意：** 如果这些回调中再次修改了 DOM，浏览器可能需要重新进行样式计算和布局，这个过程可能会发生多轮，直到信息稳定。浏览器有机制防止无限循环。
        
5. **绘制 (Paint)：** 将元素的像素数据绘制出来。
    
6. **渲染一帧页面：** 将绘制结果显示到屏幕上。
    

#### Step 5: `requestIdleCallback`（可选）😴

**如果本帧还有剩余时间**（即在一帧的 16.6ms 内，完成了前面所有任务后还有空闲时间），浏览器可能会调用 **`requestIdleCallback`** 的回调。

- **用途：** 适合执行 **低优先级的任务**，如数据预加载、预计算、上报埋点、缓存整理等。
    
- **注意：** 浏览器空闲时才触发，**不保证每一帧都会触发**。
    

#### Step 6: 进入下一轮 🔄

至此，一轮事件循环结束。事件循环会**无限重复**这个过程，从 Step 1 开始，取出下一个宏任务执行，以此类推。

一轮的完整流程概括：

$$\text{宏任务} \rightarrow \text{清空所有微任务} \rightarrow (\text{可选})\text{ 渲染/更新} \rightarrow (\text{可选})\text{ requestIdleCallback} \rightarrow \text{下一轮}$$

## 🔍 总结与对比：计时器的具体流程

以 `setTimeout` 为例，进一步说明 Web API 与事件循环的协同：

1. **JS 引擎提交任务：** 当执行 `setTimeout(() => { console.log('1s后执行') }, 1000)` 时，JS 引擎（V8）本身不负责计时，它只是将这个“定时请求”交给浏览器的**定时器模块**（属于 Web API）。
    
2. **Web API 计时：** 定时器线程开始在后台计时。
    
3. **回调入队：** 1000 毫秒时间到后，定时器线程会将回调函数 `() => { console.log('1s后执行') }` 包装成一个**宏任务**，推入 **宏任务队列** 中。
    
4. **事件循环执行：** 事件循环会在未来的某一轮中，从宏任务队列中取出这个任务，并交给 JS 引擎执行，最终输出日志。

## 2. 执行 Observer 回调与重绘、重排的关系 🖼️

**执行 Observer 回调本身并不是直接触发“重绘/重排”的原因，而是发生在浏览器判断需要渲染更新的流程中。**

在您提供的流程中：

1. 浏览器在一轮事件循环中清空微任务队列后，会判断是否需要进行**渲染更新**。
    
2. 如果需要，它会先执行**样式计算 (Style)** 和**布局 (Layout)**（即重排）。
    
3. 紧接着，浏览器会执行 **Observer 回调**，例如 `ResizeObserver` 和 `IntersectionObserver`。
    

**关键点在于：Observer 回调可能成为** **后续** **重绘/重排的原因。**

- **`ResizeObserver`** 在元素尺寸发生变化后触发。
    
- **`IntersectionObserver`** 在元素进入或离开可视区时触发。
    

如果在这些 **Observer 回调函数内部**，您又编写了修改 **DOM 结构或样式**的代码，那么浏览器就必须**重新执行**样式计算和布局，以确保最新的 DOM 状态正确地反映在屏幕上。

## 3. 无限循环的样式计算和布局及其防止机制 ⚠️

### 哪种情况会发生无限循环？

无限循环的样式计算和布局（即**重排**）主要发生在 **Observer 回调**中，特别是 **`ResizeObserver`** 的回调。

**发生机制：**

1. 代码修改了元素 A 的尺寸。
    
2. 浏览器执行样式计算/布局，发现元素 A 尺寸已变。
    
3. 触发 `ResizeObserver` 针对元素 A 的回调函数。
    
4. 在回调函数内部，代码又**再次修改**了元素 A 的尺寸（或任何其他影响布局的属性，如修改了元素 B 的尺寸，而元素 B 影响元素 A 的尺寸）。
    
5. 浏览器发现 DOM/样式再次变更，被迫**再次**执行样式计算/布局。
    
6. 这个新一轮的样式计算/布局又再次触发 `ResizeObserver` 回调... 形成一个无限循环。
    

**例子：**

JavaScript

```
const box = document.getElementById('box');
const observer = new ResizeObserver(entries => {
    // 假设这里会修改 box 的高度，而这个修改又会导致 ResizeObserver被触发
    box.style.height = `${entries[0].contentRect.height + 10}px`; 
});
observer.observe(box);
```

### 浏览器如何防止无限循环？

为了避免这种性能灾难，现代浏览器（如 Chrome/Blink 内核）会对这种**连续的、由回调触发的样式和布局更新**进行限制。

- **限制轮次：** 浏览器通常会设置一个最大迭代次数（例如，Blink/Chromium 引擎中可能限制在 **16 轮**左右）。
    
- **错误处理：** 如果在连续的几轮中，每次渲染更新后都会被 `Observer` 回调中的 DOM 修改强制再次进行样式计算和布局，达到这个最大限制后，浏览器就会：
    
    - **中断**进一步的样式计算/布局和回调执行。
        
    - 在控制台输出一个 **警告/错误**，提示开发者发生了无限循环的布局强制。
        

通过这种机制，浏览器可以保护自身不因开发者代码中的逻辑错误而进入死循环，从而避免主线程永久卡死。

是的，您的理解非常准确！**反复的、连续的重排（Layout/Reflow）和重绘（Paint/Repaint）才是导致浏览器渲染卡顿的根本原因。**

## 🎯 核心观点：反复触发的性能影响

### 1. 渲染性能卡顿的本质

**重排（Layout/Reflow）** 和 **重绘（Paint/Repaint）** 本身是浏览器渲染页面所必需的步骤。一帧内的重排和重绘是正常且必要的。

**卡顿的本质在于：**

- **执行代价高：** **重排**（重新计算元素的几何位置和大小）是所有渲染操作中代价最高的。它通常需要遍历和重新计算 DOM 树的大部分节点。
    
- **连续触发：** 每一轮事件循环（或每一帧）中，浏览器执行一次重排和重绘是没问题的。但如果因为代码逻辑错误，导致在一帧的时间内（通常是 16.6ms）**多次**、**重复**地触发重排和重绘，就会严重消耗主线程资源，导致帧率下降，用户体验感知为**卡顿**。
    

### 2. Observer 回调与卡顿的关联

您说的**Observer 回调（特别是 `ResizeObserver`）一直触发，导致需要重新计算样式和布局**，正是产生这种反复重排和卡顿的**常见机制**。

- **正常流程：** 浏览器渲染 $\rightarrow$ 样式计算/布局 $\rightarrow$ 执行 Observer 回调。
    
- **卡顿机制：**
    
    1. Observer 回调被执行（例如，因为元素尺寸改变）。
        
    2. **在回调函数内部，代码又修改了 DOM/样式。**
        
    3. 这次修改强制浏览器在渲染流程中**重新**进行样式计算和布局。
        
    4. 这次新的计算/布局又再次满足了 Observer 的触发条件。
        
    5. 循环回到第 1 步，如此往复。
        

这种**“布局 $\rightarrow$ 回调 $\rightarrow$ 强制新布局”**的循环，极大地延长了渲染一帧所需的时间，直到浏览器强制中断（如前所述的 16 轮限制），或者直到回调函数中的逻辑不再导致 DOM 变更。

**因此，卡顿的直接原因是“反复的样式计算和布局”，而 Observer 回调中的错误代码是引发这种反复行为的“导火索”。**

## 💻 示例：Scroll 和 Resize 事件回调

### 场景背景

`scroll` 和 `resize` 事件非常容易高频率触发（例如，用户快速滚动页面或拖动浏览器窗口边缘）。如果每次事件触发都立即执行回调，会大量消耗 CPU 资源，导致卡顿。

浏览器通常会对这些事件进行**节流（Throttling）** 或在**下一帧渲染前**统一处理。在事件循环的 Step 4（是否进行渲染更新？）中处理它们，就是为了在浏览器准备更新屏幕时，一次性执行最新的回调。

### 1. `resize` 事件示例

当用户拖动浏览器窗口边缘改变大小时，会触发 `resize` 事件。

**HTML & JS 代码：  HTML 和 JS 代码：**

HTML

```
<div id="status">窗口大小变化状态: 100x100</div>

<script>
    const statusDiv = document.getElementById('status');
    let resizeCount = 0;

    window.addEventListener('resize', () => {
        // 1. 当用户拖动窗口时，此回调被安排为宏任务或由浏览器优化处理
        // 2. 在事件循环进入渲染更新阶段时，浏览器会处理队列中等待的 resize 事件回调
        const width = window.innerWidth;
        const height = window.innerHeight;
        resizeCount++;

        // 实际应用场景：
        // 重新计算并调整 canvas 尺寸、响应式布局逻辑、或重新初始化某些库
        
        statusDiv.textContent = `窗口大小变化状态: ${width}x${height} (总触发次数: ${resizeCount})`;
        
        // 注意：这里执行的代码量必须小而快，以避免延迟渲染
        // 如果这里修改了影响布局的 DOM，则需要紧接着执行样式计算/布局
    });
</script>
```

**渲染更新阶段的动作：**

- 当用户快速调整窗口大小（可能触发了 100 次 `resize` 事件），浏览器可能不会在每次事件发生时都立即执行回调。
    
- 在**渲染更新阶段**，浏览器检查是否有待处理的 `resize` 回调。如果有，它会执行这些回调，**一次性**将 `statusDiv` 更新为最新的窗口尺寸。

### 2. `scroll` 事件示例

当用户滚动页面时，会触发 `scroll` 事件。

**HTML & JS 代码：  HTML 和 JS 代码：**

HTML

```
<div id="scroll-info" style="position: fixed; top: 0;">滚动位置: 0</div>
<script>
    const scrollInfo = document.getElementById('scroll-info');
    let scrollCount = 0;

    document.addEventListener('scroll', () => {
        // 1. 用户快速滚动页面
        // 2. 在事件循环的渲染更新阶段，浏览器会处理等待的 scroll 事件回调
        const scrollTop = document.documentElement.scrollTop;
        scrollCount++;

        // 实际应用场景：
        // 悬浮导航栏的显示/隐藏、视差滚动效果的计算、懒加载图片的加载判断
        
        scrollInfo.textContent = `滚动位置: ${scrollTop}px (总触发次数: ${scrollCount})`;
    });
</script>
```

**渲染更新阶段的动作：**

- 用户快速滚动一秒钟可能产生数十个 `scroll` 事件。
    
- 浏览器为了避免卡顿，会将这些回调延迟到**下一个渲染帧**之前。
    
- 在**渲染更新阶段**，浏览器会执行最新的 `scroll` 回调。由于即将进行绘制，主线程可以高效地执行这个回调，然后立即进行绘制，确保用户看到最新的滚动位置和 UI 更新，而不会因为高频事件处理而丢帧。
    

**总结：**

在渲染更新阶段处理这些事件回调，保证了回调执行发生在**最接近屏幕绘制**的时机，从而：

1. **减少不必要的计算：** 在两次绘制之间，即使触发了多次事件，也只需要执行一次回调来反映最终状态。
    
2. **避免主线程阻塞：** 将高频事件处理与页面绘制同步，防止事件处理逻辑阻塞后续的渲染步骤。

## 那一帧内不是会只触发一个宏任务吗，scroll如果有很多的回调回来的话，是不是就不止一个宏任务了


这是一个非常好的、深入事件循环细节的问题！您对“一帧内只触发一个宏任务”的理解是基于 **事件循环的基础规则**，但针对高频事件如 `scroll`，浏览器的处理机制更复杂，并涉及对宏任务的**优化和合并**。

---

## 🧐 Scroll 事件与宏任务的优化机制

### 1. 基础规则：一轮只取一个宏任务

在标准和概念上，事件循环的**一轮（Loop Iteration）** 确实是：

$$\text{取出一个宏任务} \rightarrow \text{执行} \rightarrow \text{清空所有微任务} \rightarrow \text{渲染}(\text{可选}) \rightarrow \text{下一轮}$$

这个规则是严格的。

### 2. Scroll 事件的宏任务优化：合并与调度

虽然 `scroll` 回调最终作为宏任务排队，但浏览器在处理**高频输入事件**时，会采用优化策略：

- **合并（Coalescing）：** 浏览器在短时间内（通常是几毫秒内）接收到大量的 `scroll` 事件时，它不会将每个事件都创建一个独立的宏任务。相反，它会**合并**这些事件。
    
- **延迟调度（Deferred Scheduling）：** 浏览器倾向于将 `scroll` 回调安排在 **下一帧的渲染更新阶段** 之前执行，而不是立即排队并被当前或下一轮事件循环的 Step 1 选中执行。
    

#### 宏任务的数量

当用户快速滚动时，浏览器不会为每一个像素的滚动都创建一个宏任务。

- **如果事件被合并：** 即使产生了 100 个滚动事件，浏览器可能只会创建一个或几个宏任务，每个宏任务包含**一组**或**最新的**滚动回调。
    
- **在渲染前执行：** 浏览器在**渲染更新阶段**（Step 4）处理 `scroll` 回调，这意味着它是在**当前宏任务执行完毕且微任务清空之后**，但**在样式计算和布局之前**，将这些等待的回调集中执行。
    

**因此，在一轮完整的事件循环中：**

1. **Step 1** 执行**当前**的宏任务（例如，一个 `setTimeout` 或一个用户点击事件）。
    
2. **Step 3** 清空所有微任务。
    
3. **Step 4** 进入渲染阶段，浏览器会**一次性**处理所有等待的 `scroll` 和 `resize` 回调。
    

这 4 步中的 `scroll` 回调执行，虽然本质上是宏任务级别的代码执行，但它被**集成**到了渲染流程中，**并不计入** Step 1 所说的“取出的那个宏任务”。它是浏览器为优化性能而特别安排的**一帧内处理输入事件**的步骤。

### 总结

- **一个宏任务/一轮：** 标准事件循环的一轮中，**确实只从宏任务队列中取出一个任务来执行**（Step 1）。
    
- **Scroll 回调的数量：** 浏览器通过**合并**高频事件，显著减少了需要排队的宏任务总数。
    
- **执行时机：** 浏览器将这些 `scroll` 回调安排在 **渲染更新前**（Step 4），与渲染管线同步，从而高效地处理大量的回调代码，而**不会打破**“一轮循环只取一个宏任务”的核心规则。
    

**最终结果是：** 即使有很多 `scroll` 回调，它们会被浏览器优化，**以最少的宏任务数**，集中在最有利的时机（渲染前）执行，以确保页面流畅。

冲突的核心在于：**“宏任务”** 既是一个**任务类型**的定义，又代表了 **事件循环调度** 的一个**步骤**。

首先确认定义：`scroll` 回调被归类为宏任务。当滚动发生时，浏览器会将其回调放入**宏任务队列**中等待。

### 2. 标准事件循环的 Step 1

标准事件循环的 Step 1 严格规定：

> **执行一个宏任务：** 从宏任务队列中取出**最老的一个**宏任务，并执行它。

如果您队列中有：`[setTimeout回调 (A), scroll回调 (B)]`。那么在下一轮事件循环的 Step 1 中，只会取出并执行 **A**。

这个步骤意味着：浏览器在决定渲染时，会检查并执行**所有等待的**高频输入事件回调，**而不需要再回到 Step 1 去取一个标准的宏任务**。

**关键在于：**

- **调度策略不同：** 浏览器将 `scroll` 和 `resize` 事件的回调**脱离**了 Step 1 的宏任务调度，并将它们直接 **集成（Integrate）** 到了渲染管线之前。

### 4. “一帧内只能执行一个宏任务”的准确理解

更准确的说法是：在一次事件循环的迭代中，**Step 1 只能从宏任务队列中取出并执行一个任务。**

但是，浏览器渲染更新（Step 4）是一个独立的复杂流程，它**内部**可以执行各种必要的代码，包括：

1. 处理 **高频事件回调**（`scroll`, `resize`）。
    
2. 执行 **`requestAnimationFrame`** 回调。
    
3. 执行 **Observer 回调** (`ResizeObserver` 等)。
    

这些在 Step 4 内部执行的回调，虽然其代码来源于宏任务的类型，但它们是浏览器为了保证 **60 FPS** 帧率而进行的**特殊调度**，**不计入** Step 1 的宏任务计数。

从任务**类型**上讲，DOM 事件回调是 **宏任务（Macrotask）**。它们的回调代码不能被微任务（如 Promise）中断，并且需要等待 JS 主线程空闲时才能执行。

这是特殊性的体现。浏览器为了实现流畅的 60 FPS 渲染，对高频事件采用了 **“与渲染同步”** 的调度策略：

- **脱离 Step 1 的宏任务队列竞争：** 浏览器不会让 `scroll` 回调与普通的 `setTimeout` 宏任务在 Step 1 中进行排队竞争。
    
- **集成到 Step 4 渲染阶段：** 浏览器将处理 `scroll` 回调的代码逻辑 **集成** 到了事件循环的 **Step 4：渲染更新阶段** 的起始部分，即在 **样式计算** 和 **布局** 发生之前。
    

### 3. 符合核心规则 (一帧一宏) 🔄

这种优化**并没有**打破 **“一轮事件循环（或一帧）只能从宏任务队列中取出一个宏任务”** 的核心规则。

|**规则/概念**|**描述**|**scroll 回调的处理**|
|---|---|---|
|**Step 1 宏任务**|**一轮循环** 只从宏任务队列取出 **一个** 任务执行。|**`scroll` 回调不占用这个名额**。如果有 `setTimeout` 和 `scroll` 在队列，Step 1 会取出 `setTimeout`。|
|**Step 4 渲染阶段**|在渲染更新发生时执行的特殊步骤，目的是同步输入和动画。|**`scroll` 回调在这个步骤被集中处理**。这是浏览器在 Step 4 内部执行的逻辑，不属于 Step 1 的宏任务调度。|

**因此：**

- 一帧内（一轮事件循环内），Step 1 **确实只执行一个** 标准宏任务。
    
- 同时，在这一帧的 Step 4 中，浏览器利用**特殊优化**处理了所有等待的 `scroll` 回调，确保了渲染的即时性和流畅性。
    

这种设计是浏览器引擎（如 Chromium/Blink）在性能和规范之间做出的平衡选择。

## ⏳ 事件循环与帧同步的机制

答案是：**不一定。事件循环的下一次迭代（下一轮宏任务的开始）不会严格等待下一帧的开始，但如果渲染被阻塞，浏览器会跳过中间的帧。**

让我们详细解析这个过程：

### 1. 事件循环是任务驱动的 (Step 1)

事件循环的启动是基于 **任务驱动** 的，而不是时间驱动的：

- **第一次循环结束：** 当第一次事件循环执行完 Step 1（宏任务）、Step 2（微任务）和 Step 3（渲染更新，耗时 $1.5\text{帧}$）后，主线程立即进入 **Step 6：进入下一轮**。
    
- **下一轮开始：** 主线程会马上开始执行 **第二次事件循环的 Step 1**：从宏任务队列中取出一个新的任务并执行。它**不会**为了等待下一帧（第 2 帧的 V-Sync 信号）而空闲。
    

### 2. 渲染的阻塞与丢帧

您提到的“1.5 帧完成”是关键。

- **V-Sync 信号：** 浏览器渲染是以 V-Sync（垂直同步信号）为节奏的，通常每 $16.6\text{ms}$ 触发一次，代表一帧的开始。
    
    - 第 1 帧 V-Sync 发生在 $T_0$.
        
    - 第 2 帧 V-Sync 发生在 $T_0 + 16.6\text{ms}$.
        
    - 第 3 帧 V-Sync 发生在 $T_0 + 33.3\text{ms}$.
        
- **您的场景分析：**
    
    - **第 1 轮循环开始：** 假设在 $T_0$ 附近。
        
    - **Step 4 渲染完成：** 耗时 $1.5\text{帧}$，即 $\approx 25\text{ms}$。所以渲染在 $T_0 + 25\text{ms}$ 附近完成。
        
    - **丢帧：** 当渲染在 $T_0 + 25\text{ms}$ 完成时，**浏览器已经错过了第 2 帧的 V-Sync 信号**（发生在 $T_0 + 16.6\text{ms}$）。
        
    - **结果：** 浏览器跳过了第 2 帧的绘制，必须等到**第 3 帧**的 V-Sync 信号（发生在 $T_0 + 33.3\text{ms}$）才能进行下一次有效的屏幕更新。
        

### 3. 下一次事件循环的 Step 4

虽然第二次事件循环的 Step 1（执行宏任务）会立即开始，但它的 Step 4（渲染更新）仍然要等待 V-Sync 信号。

|**循环/帧**|**关键事件**|**发生时间（ms）**|**结论**|
|---|---|---|---|
|**第 1 轮循环**|宏任务/微任务执行|$T_0 \to T_0 + 5$|-|
|**第 1 轮循环**|Step 4 渲染完成|$T_0 + 25$|**错过了第 2 帧 V-Sync (16.6ms)**。浏览器绘制了一帧，但显示给用户时已超过第 2 帧的截止时间。|
|**第 2 轮循环**|Step 1 宏任务开始|$\approx T_0 + 25$|**立即开始**，不等待 V-Sync。|
|**第 2 轮循环**|Step 4 渲染开始|$\approx T_0 + 33.3$|必须等待**第 3 帧的 V-Sync 信号**才能开始下一次渲染更新。|

**因此：**

- **下一轮宏任务（Step 1）**：**不会**等到第 2 帧开始，它会在 $T_0 + 25\text{ms}$ 时立即开始。
    
- **下一次渲染（Step 4）**：必须等到 $T_0 + 33.3\text{ms}$（第 3 帧）的 V-Sync 信号才会开始。
    

**卡顿的本质** 是：JS 任务（宏任务）或渲染工作占用了太多时间，导致我们错过了固定的 $16.6\text{ms}$ 渲染时机，使得浏览器被迫跳过一帧或多帧的显示。

## 🧐 `requestIdleCallback` 的调度机制

### 1. rIC 的核心作用：利用剩余时间 (Step 5)

`requestIdleCallback`（rIC）是浏览器提供的一种机制，用于在主线程有**空闲时间**时执行低优先级的、不紧急的任务。

- **执行时机：** 它总是在 **一轮事件循环的 Step 4 (渲染更新)** 完成之后，并且**只在**当前帧的 $16.6\text{ms}$ 预算内还有**剩余时间**时，才会执行 (Step 5)。
    
- **特性：** rIC 任务通常被封装成**宏任务**，但其执行的优先级是 **极低** 的，它必须让位给所有其他重要任务（宏任务、微任务、渲染更新）。
    

### 2. 回顾前一轮的耗时场景

我们继续沿用前一个场景：

|**循环/帧**|**关键事件**|**发生时间（ms）**|
|---|---|---|
|**第 1 轮循环**|宏任务/微任务执行|$T_0 \to T_0 + 5$|
|**第 1 轮循环**|Step 4 渲染完成|$T_0 + 25$|
|**第 2 轮循环**|Step 1 宏任务开始|$\approx T_0 + 25$|
|**第 2 轮循环**|Step 4 渲染开始|$\approx T_0 + 33.3$|


### 3. rIC 在此场景中的行为

#### rIC 不会影响 Step 1

即使您在代码中调用了 `requestIdleCallback(myTask)`：

1. 当第 1 轮循环在 $T_0 + 25\text{ms}$ 结束时，由于 **渲染工作本身就超时了** ($25\text{ms} > 16.6\text{ms}$)，浏览器判断 **当前帧没有剩余空闲时间**。
    
2. **Step 5 (rIC)** 会被跳过。`myTask` 不会在 $T_0 + 25\text{ms}$ 之前执行。
    
3. **Step 6 (下一轮开始)** 仍然会立即触发，在 $T_0 + 25\text{ms}$ 附近开始执行**下一个宏任务**（Step 1）。
    

**结论：** 在前一轮任务超时的场景中，**`requestIdleCallback` 不会执行，因此它不会成为导致下一轮事件循环（Step 1）延迟到第 2 帧才开始的原因。**

#### rIC 执行的特殊性

`requestIdleCallback` 的回调（例如 `myTask`）最终会在浏览器**真正空闲**的时候，以 **宏任务** 的形式被安排到队列中，然后被事件循环的 Step 1 选中执行。

所以，与其说 rIC 是在 Step 5 执行，不如说 Step 5 是浏览器判断 **是否安排 rIC 宏任务到队列** 的时机。如果被安排了，它仍然需要等待：

1. **所有等待的宏任务**（如 `setTimeout`）执行完毕。
    
2. 浏览器空闲。
    

`requestIdleCallback` 是一种**消极的调度**，它总是让步于所有其他任务。

## 💡 事件循环、任务与帧的协同工作

我们可以这样总结您的理解，并进行最后的精炼：

### 1. 事件循环是连续的，渲染是周期性的

- **事件循环 (Event Loop) $\rightarrow$ 连续进行：** 事件循环是一个永不停止的 `while(true)` 循环，它的目标是**尽可能快地**处理完宏任务队列中的所有任务。在一轮宏任务执行、微任务清空后，它会立即进入下一轮，**不等待帧的开始**。
    
- **渲染 (Rendering) $\rightarrow$ 周期进行：** 渲染是受 V-Sync 信号约束的，通常每 $16.6\text{ms}$（即一帧的周期）才会尝试进行一次屏幕更新。
    

### 2. 渲染延迟与丢帧

- **如果第一轮循环的渲染工作超时（耗时超过 $16.6\text{ms}$）：** 比如在 $25\text{ms}$ 完成。
    
    - 浏览器**错过了**第 2 帧的 V-Sync 信号。第 2 帧因此**丢弃/跳过**。
        
    - 主线程会在 $25\text{ms}$ 处立即开始第 2 轮事件循环的 **Step 1 宏任务**。
        
    - **第一次渲染的绘制结果**可能会等到第 3 帧 V-Sync（$\approx 33.3\text{ms}$）时才真正显示到屏幕上。
        

### 3. 多轮循环的渲染合并

您的关键点在于：**“如果两轮循环的渲染工作都在第二帧完成，那么就同时渲染。”**

这非常准确，但需要明确是 **“第二轮循环的渲染尝试”** 等待了 **“第三帧的 V-Sync”**。

1. **第一次渲染请求 (R1)**：在第 1 轮循环的 Step 4 产生，但完成太晚（$25\text{ms}$），错过了第 2 帧。
    
2. **第二次渲染请求 (R2)**：在第 2 轮循环的 Step 2（执行宏任务）中，JS 代码可能又修改了 DOM，产生了第二次渲染需求。
    
3. **合并渲染：** 当第 2 轮循环进行到 Step 4 时，它发现已经临近 **第 3 帧** V-Sync（$\approx 33.3\text{ms}$）。
    
4. 浏览器会执行一次 **“统一的渲染更新”**。这次更新会包含 **R1 和 R2 两次修改的最终结果**，并只进行一次样式计算、布局和绘制，最终在第 3 帧显示。
    

**所以，正确的理解是：** 事件循环一直在跑，但所有的渲染需求都会被浏览器**缓存**起来，直到下一个可用的 V-Sync 信号到达时，浏览器会**一次性地、高效地**将所有累积的 DOM 和样式修改计算并绘制出来，即使这些修改是跨越多轮事件循环产生的。

## 🚀 `requestAnimationFrame` (rAF) 的三大作用

### 1. 与浏览器渲染同步 (核心作用)

rAF 的回调函数会被安排在浏览器下一次 **重绘（Paint）** 之前执行。

- **避免丢帧和卡顿：** 传统的动画方法（如使用 `setTimeout` 或 `setInterval`）无法保证执行时机与浏览器的绘制周期（通常为 $16.6\text{ms}$ 一帧）同步。这可能导致回调函数在两次绘制之间执行多次，或者在绘制周期结束后才执行，从而造成画面撕裂（Tearing）或动画卡顿。
    
- **锁定 60 FPS：** rAF 确保回调函数只执行一次，执行时机正好是浏览器准备绘制新帧的时候。这使得动画的更新频率与屏幕的刷新率（通常是 60 帧/秒）保持一致，最大程度保证了动画的流畅性。
    

### 2. 节省资源和性能

rAF 具有自动暂停和恢复机制，有助于节省 CPU 资源：

- **后台自动暂停：** 当用户的浏览器标签页切换到后台，或最小化窗口时，rAF 的回调执行会自动暂停。
    
- **自动恢复：** 当标签页再次被激活或窗口最大化时，rAF 会自动恢复执行。
    
- **好处：** 避免在用户看不到页面的情况下，动画代码仍然持续运行和消耗计算资源。
    

### 3. 在事件循环中的特殊位置

rAF 的回调执行被集成在事件循环的 **Step 4 (渲染更新阶段)** 中，其执行顺序非常关键：

$$\text{宏任务} \rightarrow \text{清空微任务} \rightarrow \text{渲染判断}$$

$$\text{如果决定渲染} \rightarrow \text{1. 处理 scroll/resize} \rightarrow \mathbf{2. 执行所有\ \text{requestAnimationFrame}\ 回调} \rightarrow \text{3. 样式/布局} \rightarrow \text{4. 绘制}$$

- rAF 的回调在 **处理 `scroll`/`resize` 回调之后** 执行。
    
- rAF 的回调在 **执行样式计算 (Style) 与布局 (Layout) 之前** 执行。
    

**这意味着：**

1. 您在 rAF 回调中进行的任何 **DOM 元素位置或样式修改**，都可以被紧接着的 **样式计算和布局** 步骤捕获，并**在同一帧内**完成绘制。
    
2. 避免了“先修改 DOM，下一帧才绘制”所带来的视觉延迟。
    

简而言之，rAF 是实现高性能、高保真度 Web 动画的首选和标准方法。

### 1. rAF 避免的是什么？

rAF 避免的不是“最终渲染合并”，而是**不必要的、多次的** DOM/样式修改，以及**跨帧的延迟**：

- **避免多次更新（对比 `setInterval`）：**

    - **rAF 保证**在给定的 V-Sync 周期内，**回调只会被执行一次**，并且这个执行时机是最佳的。
        
- **避免跨帧延迟（确保立即绘制）：**
    
    - 如果在 JS 代码中修改了 DOM，但这个修改发生在上一帧的绘制之后，那么用户必须等到下一帧的 V-Sync 信号才能看到变化。
        
    - **rAF 保证**其回调函数在 **样式计算 (Style) 与布局 (Layout) 之前**执行。这意味着 rAF 中所有的动画计算和 DOM 修改，都会被紧接着的渲染步骤立即捕获，并在**同一帧内**完成绘制。
        

### 2. rAF 与渲染合并

rAF 确实参与了渲染合并，但它不是合并的**原因**，而是**优化合并**的工具：

- **rAF 是一个回调函数：** 它只是执行动画更新的代码。
    
- **渲染合并是浏览器的机制：** 无论您是否使用 rAF，浏览器都会自动将同一帧内所有 JS 导致的 DOM/样式修改进行**合并**，只执行一次样式计算、布局和绘制。
    
- **rAF 的贡献：** rAF 确保了动画更新的代码（改变元素位置、大小的代码）运行在了**最佳的位置**，即：在 **其他事件回调**（如 `scroll`）之后，以及在 **代价最高的样式计算/布局** 之前。这使得浏览器能最高效地执行一次完整的渲染流程。
    

**总结来说：** rAF 是为了保证 **高效的单次渲染** 而设计的，而不是为了解决“多次渲染合并”的问题。它确保了您在回调中进行的 DOM 操作能及时地反映在当前帧的绘制中。

## 🚀 `requestAnimationFrame` (rAF) 详解

`requestAnimationFrame` 是 Web API 提供的一个方法，它是浏览器中用于创建高性能、流畅动画的**首选标准方法**。

### 一、基本用法和语法

`rAF` 的作用是通知浏览器：你希望在浏览器下一次执行**重绘**之前运行你提供的回调函数。

#### 1. 语法

JavaScript

```
window.requestAnimationFrame(callback);
```

- **`callback` (必需)**：一个回调函数，浏览器将在下一次绘制之前调用它。
    
- **返回值**：一个用于取消回调的整数 ID (类似于 `setTimeout` 的返回值)，可以使用 `cancelAnimationFrame(ID)` 来停止动画。
    

#### 2. 回调函数的参数

回调函数被调用时，会接收一个参数：

JavaScript

```
function step(timestamp) {
    // timestamp: 自文档创建以来经过的毫秒数
    // 浏览器会在下一次绘制前自动传入这个精确的时间戳
    console.log(`当前帧时间戳: ${timestamp}`);
    // 在这里执行动画更新逻辑
    
    // 关键：为了实现连续动画，必须在回调结束时再次调用 rAF
    window.requestAnimationFrame(step); 
}

window.requestAnimationFrame(step);
```

### 二、核心作用与事件循环背景

`rAF` 的核心价值在于它与浏览器的 **垂直同步（V-Sync）** 信号和事件循环的 **渲染阶段** 完美同步。

|**作用**|**详细说明**|
|---|---|
|**与 V-Sync 同步**|保证回调函数仅在浏览器**准备绘制新帧**时执行。通常是每 $16.6\text{ms}$ 一次（60FPS）。这确保了动画更新频率与屏幕刷新率一致，避免了画面撕裂和丢帧导致的卡顿。|
|**最佳执行时机**|rAF 回调被安排在事件循环的 **渲染更新阶段**。它在**处理高频事件**（如 `scroll`）之后，以及在执行 **样式计算** 和 **布局（重排）** 之前执行。|
|**性能优化**|浏览器在标签页最小化或切换到后台时，会自动 **暂停** rAF 的执行。这避免了在用户不可见的情况下继续消耗 CPU 和电池资源。|

### 三、详细易懂的例子：平滑移动的方块

我们来实现一个使用 `rAF` 让方块在屏幕上平滑移动的动画。

#### 1. HTML 结构

HTML

```
<div id="box" style="width: 50px; height: 50px; background: blue; position: absolute; left: 0px;"></div>
```

#### 2. JavaScript 实现

JavaScript

```
const box = document.getElementById('box');
let startTime; // 用于记录动画开始时间

function animate(timestamp) {
    // 1. 初始化开始时间
    if (!startTime) {
        startTime = timestamp;
    }
    
    // 计算动画已经进行了多少时间 (ms)
    const elapsed = timestamp - startTime;
    
    // 2. 根据时间计算位置 (确保动画是基于时间，而不是 CPU 速度)
    // 目标：每秒移动 100 像素
    const distancePerSecond = 100;
    const newPosition = (elapsed / 1000) * distancePerSecond;
    
    // 3. 更新 DOM 样式
    // 这是在 Step 4 中，样式计算/布局之前执行的 DOM 修改
    box.style.left = `${newPosition}px`; 
    
    // 4. 判断是否继续动画
    if (newPosition < 300) {
        // 关键：再次请求下一帧的回调，实现连续动画
        requestAnimationFrame(animate); 
    } else {
        console.log("动画完成。");
    }
}

// 启动动画
requestAnimationFrame(animate);
```
