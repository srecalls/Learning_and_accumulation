# 背景：项目规范存在可优化部分

- 存量代码可优化，出现大量检查规范警告
    
![[项目规范优化可执行方案（更新至2.2）.png]]

- 项目代码提交描述可优化
    
![[项目规范优化可执行方案（更新至2.2）-1.png]]

### 问题分析：

- 存量代码可优化，修改成本高（现在的代码想改不敢改）
    
    - 经eslint检测，目前仅【国内开发者站运营后台】存在2250 条代码规范问题 (2122 错误, 128 告警)。逐一修改需要消耗开发、产品、测试人员大量时间
        
    - 存量代码均为已上线代码，修改易出现线上错误，影响项目正常交付，造成严重事故。
        
- 代码规范可优化，只有告警，可以跳过（未来的代码要改不想改）
    
    - 告警代码不影响代码正常提交，开发人员可自行跳过告警检测。
        
    - 告警代码在CR中不易检测，造成错误规范存量代码日益增多。
        
- 提交描述可优化，没有强制检查机制（提交描述随便写）
    
        
    - 对于刚接触项目且并不熟悉提交规范的开发人员，易造成提交不规范，导致难以直观判断提交代码类型。
        

### 解法：建立一套代码规范自动检查机制

- **强制性**：
    
    - 将告警提示修正为错误提示，代码检查不允许跳过
        
    - 对代码提交规范进行强制校验，错误规范提交不允许通过
        
- **渐进式**：
    
    - 对增量代码所处项目文件进行规范检查，逐步减少存量代码内错误规范问题。
        
    - 对增量代码提交描述进行校验，逐步对存量代码提交描述进行修正。
        
- **一致性**：
    
    - 检查机制跟随项目版本，确保每个开发人员均能按照方案进行代码规范检测开发。
        

  

## 工具（技术选型）

  eslint、husky、lint-staged、commitlint、commitizen

## 方案实现

### 强制性

1. 代码规范
    

`eslint`工具能对开发代码进行配置规则校验

造成代码规范执行不到位的主要问题是由于代码检查中出现的告警提示是允许被跳过的，因此利用到`Git Hooks`中的`pre-commit`，对`pre-commit`进行配置，对开发人员的代码进行强制检测，强制按照规定的代码规范对项目进行需求开发，修正开发习惯。

`pre-commit`(预先提交) 这个钩子由`[git commit](https://git-scm.com/docs/git-commit)`调用，它不接受任何参数，并在获取建议的提交日志消息和进行提交之前被调用。可以通过这个Hook进行配置，对用户的代码进行强制规范性检测，修正错误规范代码。

  

2. 提交规范
    

`commitlint`工具能对代码提交描述进行规范性检查。

通过工具文件`commitlint.config.js`进行配置，可以通过`npx commitlint --edit`对提交的描述进行规范性检查。此处可以通过`Git Hook`的`commit-msg`处对提交的代码进行检查。

- `-e, --edit`: 从指定文件中读取最后一次提交的消息，或者回退到 `./.git/COMMIT_EDITMSG`。[字符串]
    

  

`commit-msg`(提交信息) 这个钩子由[git commit](https://git-scm.com/docs/git-commit)和[git merge](https://git-scm.com/docs/git-merge)调用，可以使用`--no-verify`选项绕过它。它接受一个参数，即保存建议的提交日志消息的文件的名称。退出非零状态会导致命令中止。

允许钩子就地编辑消息文件，并可用于将消息规范化为某些项目标准格式。它还可用于在检查消息文件后拒绝提交。

  

### 渐进型

1. 代码规范
    

利用`lint-staged`对增量代码所处的文件进行规范性检测，渐进式修正项目代码规范。

lint-staged 是一个npm 包，作用是只检查的在暂存区内待提交的文件，而不是全部的代码。

```JSON
  "lint-staged": {
  // 此处配置作用为对后缀为.js, .ts, .jsx, .tsx进行eslint修复后，进行eslint检查
    "*.{js,ts,jsx,tsx}": [
      "eslint --fix"
    ]
  }
```

`--fix`

此项指示 ESLint 尝试修复尽可能多的问题。这些修复是对实际文件本身进行的，只有剩余的未修复的问题才会被输出。需开发人员对eslint进行修复后仍存在代码规范问题的代码进行进一步的修正。

  

2. 提交规范
    

`commitlint`仅对开发人员本次提交的代码进行提交描述规范性校验。

- 增量代码
    
    - 对增量代码进行提交规范校验约束后续不规范提交描述的发生
        
- 存量代码
    
    - 在开发过程中涉及对存量代码修改的项目，进行重新提交`commitlint`校验，渐进式修改。
        

### 一致性

对于任何Git仓库来说钩子都是本地的，而且它不会随着`git clone`一起复制到新的仓库。而且，因为钩子是本地的，任何能接触得到仓库的人都可以修改。在开发团队中维护钩子是比较复杂的，因为`.git/hooks`目录不随你的项目一起拷贝，也不受版本控制影响。一个简单的解决办法是把你的钩子存在项目的实际目录中（在.git外）。这样你就可以像其他文件一样进行版本控制，为了解决这个问题，引入了husky这个工具。

  

husky 是一个 Git Hook 工具。husky 其实就是一个为 git 客户端增加 hook 的工具。将其安装到所在仓库的过程中它会自动在`.git/`目录下增加相应的钩子实现在`pre-commit`阶段就执行一系列流程保证每一个`commit` 的正确性，在`commit-msg`阶段执行一系列流程保证每一个代码提交描述的正确性。

  

在git 2.9之后，git 添加了一个配置功能，`core.hooksPath`, 可以指定hooks目录不在使用.git/hooks/。

`husky install`命令 会创建.husky目录，并且执行 **`git config –local core.hooksPath .husky`**, 修改hooks目录。

在使用git hook前需要手动输入`husky install`命令修改hooks的目录才能进行配置后hook的使用，因此需要在`script`中添加`"prepare": "husky install"`。

`prepare`：在打包和发布包之前运行，在`npm install`没有任何参数的本地运行。

## 1.0

### 方案文件配置

#### package.json

```JSON
{
  "scripts": {
    // ...其他配置
    "prepare": "npx husky install && husky add .husky/pre-commit \"npx lint-staged\" && husky add .husky/commit-msg \"npx --no-install commitlint --edit '$1'\""
    
    // 由于
    // 此处不直接对.husky文件中commit-msg与pre-commit进行配置。
  },
  "lint-staged": {
    "*.{js,ts,jsx,tsx}": [
      "eslint --fix"
    ]
  },
  "devDependencies": {
  // 使用"husky":"^7.0.1"
    "husky": "^7.0.1",
    "lint-staged": "^11.0.1",
    "@commitlint/cli": "^12.1.4", // 这个包提供了一个命令行工具，用于在代码提交之前验证提交信息的格式和规范。
    "@commitlint/config-conventional": "^12.1.4" // 这个包是 @commitlint/cli 的一个预定义配置包，其中包含了针对约定式提交规范的配置。
   }
}
```

  

在husky@4中，`husky`在`package.json`中进行配置，husky会在`.git/hooks,` 写入所有的hooks脚本，里面的命令都是执行`husky.sh`。

而husky.sh里面的脚本，就是获取你在`package.json`里面配置的`husky.hooks` 里面的键值对。如果当前脚本名和”键”对应上，就执行后续”值”的命令。所以每次的git操作，都会触发所有的`hook`脚本。

```JSON
// package.json 
  "husky": {   
     "hooks": {     
         "pre-commit": "npm test"   
     } 
   } 
```

这也导致了如果已经有了某个脚本，`husky`是不会覆盖掉的，也造成了部分代码库，在部分开发人员上好使，在部分开发人员上不好使的情况。

而在Husky@7中采用的就是上述方案实现中一致性里的内容，修改`hooks`地址，在`.husky`文件中写入对应的钩子的脚本文件，在指定操作后触发对应的钩子从而执行脚本文件，比如使用`git commit` 触发`pre-commit`。

而采用过高的版本包会导致与项目node版本产生冲突。

因此，此处决定采用`husky@7`与`lint-staged@11`作为项目依赖。

  

#### .husky/pre-commit

```Bash
#!/bin/sh
. "$(dirname "$0")/_/husky.sh"

npx lint-staged
```

在husky注册`pre-commit`钩子，当钩子触发时执行脚本`npx lint-staged`对代码进行规范校验。

  

#### husky/commit-msg

```Bash
#!/usr/bin/env sh
. "$(dirname -- "$0")/_/husky.sh"

npx --no-install commitlint --edit "$1"
```

在husky注册commit-msg钩子，当钩子触发时执行脚本 `npx --no-install commitlint --edit "$1"`对提交描述进行规范校验。

  

#### commitlint.config.js

```Java
module.exports = {
  // 继承的规则
  extends: ['@commitlint/config-conventional'],
  // 定义规则类型
  rules: {
    // type 类型定义，表示 git 提交的 type 必须在以下类型范围内
    'type-enum': [
    // 验证的错误级别
      2,
      // 什么情况下进行验证
      'always',
      [
        'feat', // 新功能 feature
         .....
      ],
    ],
  },
};
```

1. #### 修改lint-staged版本不兼容问题
    

针对`@mi/commition`中`converters/commit-spec`进行如下修改

```JavaScript

const semver = require('semver');
// semver 是一个Node.js内置模块，用于解析和比较版本号的工具库。
const currentVersion = process.version;
// 通过process.version获取当前开发环境的Node版本

  const hasInstalledCommitlint = fs.existsSync(path.join(projectNodeModuleDir, '@commitlint'));
  if (!hasInstalledCommitlint) {
    packages.push('@commitlint/cli');
    packages.push('@commitlint/config-conventional');
  }


packages.push('@commitlint/config-conventional');
 


const packages = ['commitizen', 'cz-conventional-changelog', 'conventional-changelog', 'lint-staged'];
const packages = [
    'commitizen',
    'cz-conventional-changelog',
    'conventional-changelog',
    '@commitlint/cli',
    '@commitlint/config-conventional'
];

let selectedVersion = null;

const lintStagedVersions = {
    v15: ">=18.12.0",
    v14: ">=16.14.0 <18.12.0",
    v13: ">=14.13.1 <16.14.0",
    v12: ">=12.20.0 <14.13.1",
    v10: ">=10.13.0 <12.20.0",
};
// 依据lint-staged工具包changelog判断下载版本

let selectedVersion = null;

Object.entries(lintStagedVersions).forEach(([version, range]) => {
    if (semver.satisfies(currentVersion, range)) {
      selectedVersion = `lint-staged@${version}`);
    }
});
packages.push(selectedVersion)
```

需要注意：

lint-staged13 最新版本v13.3.0不支持node.js14版本，与v14同为支持大于16.14.0，小于18.12.0版本的node，因此当项目node版本处于该区间时，自动采用最新lint-staged14版本。

## 2.2

### 背景

开发项目时无法得知当前项目使用Node版本，开发人员基于同一项目开发无统一Node环境规范。

### 问题

- 未指定项目node版本：当前部分项目如【国内开发者站运营后台】【开发者站】项目在`package.json`中未指定使用的Node版本。
    
- 未说明项目Node版本：当前部分项目如【国内开发者站运营后台】【开发者站】项目在`README.md`中未说明Node版本。
    
- 环境未统一：在开发人员
    

###   解决

####     package.json修改

1. 指定项目Node版本：在当前的每个项目的`package.json`，依据当前项目上线环境Node版本进行配置。
    

    此处以【开发者站】为例：

  

> ![[项目规范优化可执行方案（更新至2.2）-10.png]]
> 生产环境node版本配置

    在 `12.10:latest` 中，`latest` 是指 Docker 镜像标签的一种命名约定。

  

    在 `package.json` 文件中，设置一个名为 `"engines"` 的字段，其中可以指定所需的 Node.js 版本范围。

```JSON
// package.json
"name": "appstore-developer-web-fe",
  "version": "0.9.145",
  "private": true,
  "engines": {
      "node": ">=12.10"
    }
  "dependencies": {
    "@ant-design/icons": "^4.2.2",
    "@elastic/apm-rum": "^5.5.0",
    ...
   }
   ...

// package.json
"name": "cms"
  "engines": {
  "node": "10.16.3"
}
```

#### README修改

2. 在README.md文件中, 添加项目Node版本说明，单独说明每个项目对应的Node版本范围。
    

```Shell
# 国内开发者站

## 项目介绍

[国内开发者站](dev.mi.com) 前端

[仓库地址](https://git.n.xiaomi.com/xiaomi-appstore/appstore-developer-web-fe)

## 项目Node版本
本项目支持Node版本(>=12.10)

## 技术选型
```

必要性：

- 可以统一开发人员所使用的node版本范围，避免与线上环境造成冲突引发严重事故
    
- 对于刚接手项目的开发人员，能更直观的看到当前项目的node版本进行配置，防止依赖的安装冲突以及项目无法运行的情况发生，提高开发效率。
