## 填写发版记录

## 确认上线时间

与服务端进行沟通，确认是前端线上线，还是后端先上线

## 合并进入上线分支

1. 代码合并：通过merge request将代码合进需要上线的release分支
    
2. 分支拉取：合并完毕后，拉取release分支
    
3. 执行npm run release对执行版本变更
    

package.json

```undefined
"release": "standard-version --tag-prefix stable-"
```

终端执行 npm run release

```SQL
> standard-version --tag-prefix stable-

✔ bumping version in package.json from 0.9.147 to 0.9.148
✔ bumping version in package-lock.json from 0.9.147 to 0.9.148
✔ outputting changes to CHANGELOG.md
✔ committing package-lock.json and package.json and CHANGELOG.md
✔ tagging release stable-0.9.148
ℹ Run `git push --follow-tags origin release/2023/10/12` to publish
```

4. 对变更后的分支，执行git push --tag进打标签推送
    

  

## 上线流程审批(审核后台除外)


进入平台发起上线流程，填写对应
![[上线流程.png]]
1. 上线描述
    

- 自行写，可以写上线时间，上线版本
    

  

2. Git 地址
    

- 上线项目的项目地址
    
    - 可以通过gitLab中看到对应项目地址
        
    
    ![[上线流程-1.png]]
    - 可以通过在命令行输入 git remote -v查看远程仓库地址
        
    
    ![[上线流程-2.png]]

  

3. 版本源
    

填写上线的版本分支，比如release/2023/10/12

  

4. 版本选择
    

选择所需要上线的分支版本
![[上线流程-3.png]]
  

5. 上线时间
    

根据“【生态业务部】上线同步群”内待上线日期进行对应上线时间的填写

  

6. 上线影响
    

填写本次上线的影响范围。（可以写对应的项目需求，需求内的修改点）

  

7. 上线步骤
    

填写本次上线的步骤。

  

8. 回滚步骤
    

填写本次回滚的步骤。

_回滚_（Rollback）指的是程序或数据处理错误，将程序或数据恢复到上一次正确状态的行为。

  

9. 是否在安全测试范围
    

根据是否涉及外网可访问域名进行对应的选择。若无则填否。

  

10. 研发审批人
    

填写此次上线审批进行审批的研发人员。必填。

  

11. 产品审批人
    

填写此次上线审批进行审批的产品人员。根据是否涉及进行选填。

  

12. 测试审批人
    

填写此次上线审批进行审批的测试人员。根据是否涉及进行选填。

  

13. 操作人
    

填写发起人

  

14. 其余字段
    

TODO

  

  

填写完毕后，选择上线审批进行流程发起。

（紧急上线：不用进行审批人审批，直接审批通过）

  

## 项目生产环境部署(审核后台除外)
![[上线流程-4.png]]
部署环境“选择“部署环境”为线上环境

代码分支：选择上线代码分支

已审批版本：选择已审批版本（此处需要进行上线流程审批后才会进行对应上线版本的展示，若未进行审批，则无版本可进行选择）

  

## 上线流程审批（针对审核后台）

1. merge进入release分支后进入CI流程。通过deploy命令进行审批。
    
2. 审批完成后自动化部署进入线上环境。
    

  

  

## 合并进入Master

等流程（小米审批）走完之后再将release分支并入master

  

## 注意事项

1. 评估部署顺序影响，服务端与前端服务谁部署是否会导致线上环境出现问题。
    
2. 针对存在问题1中部署顺序导致的上线时间差问题的上线请求，分阶段进行上线。
    
3. 注意同步问题，在上线流程时刻与服务端与产品同步。
