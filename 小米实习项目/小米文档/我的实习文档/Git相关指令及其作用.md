# Merge

```undefined
git merge <branch>
```

用于将一个分支的更改合并到另一个分支。它的作用是将不同的代码分支合并为一个统一的代码基础，以便确保分支之间的代码同步和一致性。

具体而言，`git merge` 的作用包括以下方面：

1. 合并分支：`git merge` 用于将一个分支（通常是一个特性分支）的更改合并到另一个分支（通常是主分支或稳定分支）上。通过合并分支，可以将不同分支上的新增、修改或删除的代码合并为一个整体。
    
2. 解决冲突：当合并分支时，如果两个分支上有相同的文件或相同的代码片段进行了不同的修改，就会发生冲突。`git merge` 提供了一套冲突解决机制，允许开发人员手动解决冲突，以确保合并结果的准确性。
    
3. 快进合并（Fast-forward merge）：如果要合并的分支是目标分支的直接上游（即目标分支没有新的提交），则 `git merge` 可以执行快进合并，直接将目标分支指向要合并的分支的最新提交。这种合并方式不会创建新的合并提交，只是简单地指向最新的提交。
    
4. 创建合并提交：当无法进行快进合并时，`git merge` 会创建一个新的合并提交。合并提交包含了要合并的分支的更改，并将其合并到目标分支上。这样可以保留分支的历史记录，并确保合并操作的可追溯性。
    

## 常见的合并策略

一些常见的合并策略包括：

- `--no-ff`：禁用快进合并（no fast-forward）。强制创建一个新的合并提交，即使存在可以直接合并的提交。
    
- `--ff-only`：只执行快进合并（fast-forward）。如果不能进行快进合并，则不执行合并操作。
    
- `--squash`：将合并的提交压缩成一个单独的提交，不保留提交历史。
    
![[Git相关指令及其作用.png]]

- `--commit`：执行合并时创建一个新的合并提交，即使可以进行快进合并。
    
- `--abort`：取消当前的合并操作，将分支恢复到合并之前的状态。
    

参数：

- `<branch>`：要合并的目标分支的名称。
    
- `<commit>`：要合并的特定提交的哈希值或引用。
    
- `<remote>/<branch>`：要从远程仓库拉取并合并的分支。

# Rebase

```SQL
git rebase <branch>
```

用于重新应用提交，改变提交历史的顺序、结构或补丁。它的作用是将一个分支的提交移到另一个分支之前，以便将更改整合到一个干净、线性的历史中。

具体而言，`git rebase` 的作用包括以下方面：

1. 合并提交：通过使用 `git rebase`，你可以将一个分支上的一系列提交合并成一个或者几个更大的提交。这有助于保持提交历史的干净、整洁和易于理解。
    
2. 变基操作：`git rebase` 可以将当前分支的提交基点移动到另一个分支上，以使当前分支的提交基于目标分支的最新提交。这样可以将当前分支的更改基于最新的代码，避免由于基点过时而引入冲突和问题。
    
3. 解决冲突：当进行变基操作时，如果当前分支的提交与目标分支或其他分支的提交冲突，就会发生冲突。在这种情况下，你可以使用 `git rebase` 的交互模式手动解决冲突，确保变基操作的顺利进行。
    
4. 重排序提交：通过使用 `git rebase`，你可以重新排序当前分支上的提交顺序。这在提交历史中重新组织代码或按照逻辑顺序显示提交时很有用。
    
5. 清理提交：使用 `git rebase` 还可以清理提交历史，包括合并冗余提交、合并连续的小提交等。这有助于保持提交历史的简洁性和可读性。
    

## 常见的合并策略

选项：

- `--onto <newbase>`：指定新的基准分支，将当前分支的提交重新应用到 `<newbase>` 分支上。
    
- `-i/--interactive`：进入交互模式，允许对提交进行选择、编辑和重排。
    
- `--continue`：在解决冲突后继续执行变基操作。
    
- `--abort`：取消当前的变基操作，恢复分支到变基之前的状态。
    
- `--skip`：跳过冲突的提交，继续应用后续的提交。
    

参数：

- `<branch>`：指定要变基的目标分支。默认情况下，`git rebase` 将当前分支作为目标分支。
    
- `<upstream>`：指定当前分支的上游分支，即确定变基的起点。如果未指定，则默认使用当前分支的追踪分支。
    
- `<newbase>`：在 `--onto` 选项中使用，指定新的基准分支。
