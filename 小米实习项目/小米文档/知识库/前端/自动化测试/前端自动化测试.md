

## 一、前言

自动化测试对于前端来说是一个比较特殊的命题，一方面大家都了解测试带来的好处可以极大的减少错误上线。另一方面，又由于前端一些页面开发周期短，迭代速度快，没有时间和精力耗费在写大量的测试代码上，所以大家很少花时间去研究和学习前端的自动化方案。

接下来我们就来了解一下为什么需要自动化测试呢？

### 为什么需要自动化测试

自动化测试能够预防无意引入的 bug，并鼓励开发者**将应用分解为可测试、可维护的函数、模块、类和组件**。这能够帮助你和你的团队更快速、自信地构建复杂的应用。

首先：我们进行测试的目的在于：

- 提高代码质量
- 准确、快速定位问题
- 方便迭代／重构
- 保证线上运营，避免存在 BUG 的代码发布上线造成损失
- 减少回归流程
- 增加开发者信心

其次，测试自动化的好处在于反馈及时，能够极大地提高前端的开发效率。需求迭代时间越久，我们的收益越高。

> 自动化测试的收益=迭代次数×全手动执行成本−首次自动化成本−维护次数×维护成本

所以，自动化测试在前端工程中也是相当重要的一部分。即使是快速迭代的活动页面，也会有通用的工具函数与 SDK，对这一部分的代码进行测试用例的完善是有必要且意义重大的，而对于某些流量巨大且长期存在的页面，我们更是需要进行多种测试场景的保障。

## 二、测试分类

![[前端自动化测试.png]]

### 2.1 单元测试（Unit Testing）

单元测试通常适用于独立的业务逻辑、类、模块或函数等，不涉及 UI 渲染、网络请求或其他环境问题。

代码中多个组件共用的工具类库、核心逻辑函数等都需要引入单元测试来保证低代码质量及后续维护。

**单元测试应该是项目中数量最多、覆盖率最高的。**

能进行单元测试的函数/组件，一定是低耦合的，这也从一定程度上保证了我们的代码质量。

单元测试并不是越细粒度越好，不是每个函数都要验证，而是我们要划分成不同的**功能单元**，针对每一个独立的功能单元进行测试。

```
// helpers.js
export function increment (current, max = 10) {
  if (current < max) {
    return current + 1
  }

  return current
}
```

```
// helpers.spec.js
import { increment } from './helpers'

describe('increment', () => {
  test('increments the current number by 1', () => {
    expect(increment(0, 10)).toBe(1)
  })

  test('does not increment the current number over the max', () => {
    expect(increment(10, 10)).toBe(10)
  })

  test('has a default max of 10', () => {
    expect(increment(10)).toBe(10)
  })
})
```

我们知道，测试用例也可以反过来对代码产生检查作用，而在单元测试阶段这种作用基本是最明显的，比如你可以很容易发现某一处功能单元设计得过于耦合，或是某一外部依赖将导致代码进入错误分支等情况。

### 2.2 集成测试（Integration Testing）

如果说单元测试是为了测试单个功能单元，那么集成测试很明显就是为了测试多个功能单元的协作。

但需要注意，这并不是说要对整个完整功能的测试，而是针对核心功能流程，测试经过单元测试后的各个模块组合在一起是否能正常工作。会对组合之后的代码整体暴露在外接口进行测试，查看组合后的代码工作是否符合预期。

### 2.3 组件测试（Component Testing）

单元测试和集成测试是前后端应用中通用的概念，当我们关注前端领域特定的功能时，就需要关注到基于特定领域的测试需求。

在当今的前端项目中，组件化应该是最明显的一个趋势，那么进行组件维度的测试也自然是相当有必要的。以 Vue 组件为例，我们可以模拟这个组件的入参，并观察其实际渲染的 UI 组件是否正确，以及使用快照的方式，来检查组件的实际渲染是否一致。

从粒度的角度来看，组件测试位于单元测试之上，可以被认为是集成测试的一种形式。

目前使用的组件测试方案通常是和框架绑定的，测试方案的选取可参考官方文档。

[vue3-组件测试](https://cn.vuejs.org/guide/scaling-up/testing.html#component-testing)

### 2.4 端到端测试（E2E Testing）

单元测试、集成测试、组件测试已经从不同场景和不同维度对产品功能进行了验证，但是我们还需要一个非常重要的维度的验证——用户视角。

要从用户的视角出发，实际上我们只需要屏蔽对程序内部的所有感知，而只是去使用这个程序即可。它不再关注内部功能单元的细节，而是完全从一个用户的角度去使用产品。

前端的端到端测试不需要关注具体使用了哪个技术架构，代码具体实现等，不引入任何技术架构代码部分，而是完全依靠在真实浏览器中浏览整个页面来测试你的应用。

通过测试用户操作如何影响你的应用，端到端测试通常是提高应用能否正常运行的置信度的关键。

## 三、采用何种测试思想

### TDD：Test-Driven Development（测试驱动开发）

TDD 要求在编写某个功能的代码之前先编写测试代码，然后只编写使测试通过的功能代码，通过测试来推动整个开发的进行。

TDD的特点：

- 需求分析，快速编写对应的输入输出测试脚本；
- 实现代码让测试为成功，仅在自动测试失败时才编写新代码。
- 重构去除不必要的依赖关系，然后重复测试，最终让程序符合所有要求。

### BDD：Behavior-Driven Development（行为驱动开发）

BDD 可以让项目成员（甚至是不懂编程的）使用自然语言来描述系统功能和业务逻辑，从而根据这些描述步骤进行系统自动化的测试。

BDD的特点：

- 从业务逻辑的角度定义具体的输入与预期输出，以及可衡量的目标；
- 尽可能覆盖所有的测试用例情况；
- 描述一系列可执行的行为，根据业务的分析来定义预期输出。例如，expect, should, assert；
- 设定关键的测试通过节点输出提示，便于测试人员理解；
- 最大程度的交付出符合用户期望的产品，避免输出不一致带来的问题。

## 四、哪些项目适合引入测试

考虑到编写测试脚本还是需要一定的人力成本，所以不是所有的项目都要引入自动化测试的。

**适合引入自动化测试的场景：**

- 公共库类的开发维护
- 中长期项目的迭代/重构
- 引用了不可控的第三方依赖

## 测试工具比较

如何选择测试框架？我们需要考虑一下几点：

- 测试框架是否有简明的语法与文档
    
- 断言(Assertions)：用于判断结果是否符合预期。有些框架需要单独的断言库
    
- 异步测试：框架对异步测试支持能力
    
- 使用的语言：大部分 js 测试框架使用 js
    
- 用于特定目的：每个框架可能会擅长处理不同的问题
    

是要测试单个功能、单个组件、还是集成化测试？

是要测试GUI逻辑、交互？

是要测试非功能性指标？兼容性？

## 测试报告

当测试失败时，提供有用的错误日志以最小化调试问题所需的时间对于组件测试框架来说至关重要。除了简单地告诉你什么测试失败了，他们还应额外提供上下文以及测试失败的原因，例如预期结果 vs. 实际得到的结果。

一份好的报告就是能够一眼就告诉你以下这些内容：

- 什么组件正在被测试
- 你期望什么行为
- 实际是什么结果
- 你期望什么结果
- 如何重现

所以我们在进行测试时，一定要表达清楚上面的内容，方便通过测试报告快速了解未通过的case是什么，快速定位问题。
