# 优化方案

## 接入elastic

1. 接入elatstic，上报具体时间节点数据(e节点前统计计入一次白屏时间）
    1. Webview加载时间
    2. DNS解析时间
    3. 页面下载时间
    4. 应用启动时间：js首次执行完成事件
    5. 首次有效绘制内容时间
    6. 应用加载完成事件

2. 根据lighthouse结果进行一版优化
3. 根据elastic分析各个环节，进行具体优化

## 具体方案

### 目前已采用方案 653 => 295

1. 移除vconsole， 减少140kb
2. 样式预加载，添加preload （提高lighthouse的评分）
3. 组件按需加载，第一次减少80kb，第二次减少70kb
4. common js优化 -----减少了2kb，没什么作用

移除vconsole，缩小组件范围，添加preload，优化commonjs后对比：
![[搜索倒流页优化方案-5.png]]
#### 优化后，共计减少220kb左右
![[搜索倒流页优化方案-6.png]]
![[搜索倒流页优化方案-7.png]]
总结：目前的解决方案治标不治本，而且虽然缩减了组件范围，但是现有的改动也比较大，组件间存在循环引用的问题，不可避免的引入component.js，将所有文件加载进来，所以要是想针对本次修改

，有两种方案：

1. 将影响的组件都复制一版到keypad-ad目录下，仅针对此页面进行构建发版
2. 将component.js里面的内容都变为按需加载的组件，这样会导致拆分的chunk多，但是没有关系，无论是cdn还是file协议引入，都没有请求数量的限制。

### 可以做但是时间成本相对高的

1. 精简css代码：（`需要配置白名单，这个规则不太好确定，搞不好就会丢失样式`）

> `问题：消除了本来有用的样式，而且我认为编译阶段是不能完成这个工作的，即便在done这个hook下，css已经完成分离，但是我们的html是个空的html啊，需要解析执行js，将dom挂载完成后，才能确定需要什么样的css，感觉这是个比较复杂的过程，插件也无能为力`

> `https://purgecss.com/plugins/webpack.html`

> `https://tailwindcss.com/docs/optimizing-for-production#removing-unused-css-with-purgecss`

2. 将commonjs改为ES module，则可以使用tree-shaking ========成本较高

https://segmentfault.com/a/1190000038204855

3. 所有组件按需加载

总结：这样做的时间成本比迁移的成本低很多，而且会有明显效果

总结：

减少js体积，一方面可以减少下载时间，另一方面可以减少解析时间。
