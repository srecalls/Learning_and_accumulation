# 本 SOP 目的

- 为了更快响应线上问题，提升问题处理效率，特制定线上问题通用SOP。
    

# 适应范围

- 对用户产生了影响的 bug
    
- 商店App中h5页面的问题，非测试已知jira
    
- 小米办公群中针对商店、开发者站、开放平台等对外平台的反馈
    
- 小米社区或者微博等平台的用户反馈
    
- 系统用户反馈的问题

# 故障定义

- 线上服务出现全部不可用、部分不可用、逻辑错误、数据丢失，影响到用户体验等情况都记做线上故障
    
- 以下渠道来源的故障高优对待：
    
    - 小米社区或者微博等平台的用户反馈
        
    - 小米手机的系统用户反馈
        
    - 涉及商业化收入的故障
        

# 故障处理

1. ## 问题确认
    

1. ### **用户安抚和赔偿用户安抚和赔偿**
    

若造成了用户体验的问题，要及时做好用户的安抚，对于造成了用户财产损失的，也需要制定赔偿方案，避免舆情发酵影响公司形象，这部分的工作通常不会落在技术团队，但大家需要为其他职能提供全面，准确的信息

2. ### 尽可能获取故障的信息，包括日志、截图、视频
    

3. ### 根据获取的信息进行复现，对故障进行评判，确认是否为问题及其严重性
    

对于外部的问题反馈，我们要保持开放的心态，也要对结论持怀疑的态度

- 【开放】要求我们不放过任何一个可疑的问题反馈，尽可能多的收集信息有助于我们分析问题并得出更加准确的结论
    
- 【怀疑】要求我们严谨的对待他人提供的信息，不应【轻易相信】外部结论，需要自己分析信息，做出自己的判断，避免在问题修复上，向一个错误的方向出发
    

举一例：“某某，我发现你们的网站崩溃了，应该是某个 css 加载导致的，你赶紧处理一下”

真正的信息：

1. 网站崩溃了
    
2. 某个 css 【可能】加载失败了
    
3. 因果关系不确定（作为系统的拥有者，你需要根据1、2有自己的判断，而非被外部的反馈限定了思维）
    

- 确认故障影响范围
    
    - 系统损坏的范围有多大？系统是可用，完全不可用，还是部分不可用？
        
    - 受损用户有多少？
        
    - 用户体验受损了吗？有多少用户反馈？
        
    - 影响收入了吗？收入影响是多少？
        

如果判断是问题，继续流程；如果判断不是问题，不需要继续处理。

4. ### 对于短时间（半天）内无法做出判断的故障，跳转到第2步做信息同步
    

**影响****收入****，涉及政府合规风险、涉政、涉密为最高优先级，必须向上同步**

2. ## **信息同步**
    

线上故障的处理意味着**受损各方**需要在**给定时间内做很多关键的决策**，而信息则是决策的关键因素，所以当遇到线上故障时，请务必首先做好信息同步，可以从两个维度考虑：

1. ### 同步相关方并拉齐相关信息
    

- 直属 leader， 你需要反馈的第一人，并 Leader 确认相关方拉飞书群，紧急情况直接线上/线下会议沟通，相关方包括
    
    - 业务方，业务方多数时候作为受损方，有权利，有必要知道事情的真相，隐瞒问题只会让事情恶化，让多方陷入焦虑
        
    - 系统的 Owner，系统的 Owner 有系统更细节，更丰富的信息，若 Owner 不是你，应该及时周知他，让他参与进来协助线上故障的高效解决
        
    - 组员，相信团队的力量以及每个人愿意帮助团队的心
        

- **同步信息时候，要包含如下关键信息**
    
    - 故障现象
        
    - 故障影响
        
    - 故障的初步分析，故障点可能发生在哪里
        
    - 你接下来准备做的动作是什么，为什么这样决策
        

2. ### 定时（视紧急程度，至少 1H 一次）同步故障处理进展
    

- 事故当前处理的阶段
    
- 需要谁具体做什么事情
    

3. ## **故障****修复**
    

1. ### 尽快降低线上收入损失和用户体验损失
    

对于线上故障，第一要务是及时止损，尽快的降低收入损失和用户体验损失，止损方案包括但不限于；**所有操作不要自己做决定，需要Leader/业务方共识**

- 检查近期所有变更，包括但不限于：
    
    - CMS 配置变更
        
    - 实验变更
        
    - 运维操作
        
    - 代码上线
        
    - 等其他变化
        
- 如果因变更引起线上问题，及时做好回滚，操作前要确认系统可回滚并周知业务方共同决策，避免不科学的回滚会带来更大的事故
    
    - 回滚后是否回导致数据兼容问题
        
    - 是否会导致数据脏写
        

2. ### **问题修复**
    

- 问题排查
    
- 修复方案（书面）的多方确认
    
- 代码的多方 Review
    
- 关联业务的及时拉通和确认
    
- preview 发布，自我验证
    
- 小范围灰度
    

4. ## **发布修复**
    

由于是线上故障，修复的时间一定是越短越好，**但也务必切记：质量才是第一要务**，切莫不经测试直接上线

5. ## **确认修复**
    

- 测试，拉通质量同学，验证系统恢复
    
- 确认系统各项指标已恢复正常
    

  

# 故障复盘

### 为什么要复盘

- 故障的发生往往不是孤立的，意味着我们的系统，工作流程中存在潜在漏洞，找到它，解决它，从而避免下次故障的发生。
    
- 复盘的目的是降低以后出现类似事故或者相关事故的几率，是一次改善工作流的机会，同时提高大家的质量意识，不是为了给个人定责或者给予惩罚，任何线上事故的出现都是对用户的一次伤害，任何事故也都会影响我们团队、应用分发部以及小米在外的信任度。
