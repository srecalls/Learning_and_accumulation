## （2） JS引擎线程
JS引擎线程也称为JS内核，负责处理Javascript脚本程序，解析Javascript脚本运行代码;JS引擎线程一直等待着任务队列中任务的到来，然后加以处理，一个Tab页中无论什么时候都只有一个JS引擎线程在运行JS程序:

## （3）事件触发线程
**事件触发线程**属于浏览器而不是JS引擎，用来控制事件循环;当JS引擎执行代码块如setTimeOut时 (也可是来自浏览器内核的其他线程,如鼠标点击、AJAX异步请求等)，会将对应任务添加到事件触发线程中;当对应的事件符合触发条件被触发时，该线程会把事件添加到待处理队列的队尾，等待JS引擎的处理;

注意:由于JS的单线程关系，所以这些待处理队列中的事件都得排队等待JS引擎处理(当JS引擎空闲时才会去执行)

## （4）定时器触发线程
**定时器触发进程**即setlnterval与setTimeout所在线程;浏览器定时计数器并不是由JS引擎计数的，因为JS引擎是单线程的，如果处于阻塞线程状态就会影响记计时的准确性，因此使用单独线程来计时并触发定时器，计时完毕后，添加到事件队列中，等待JS引擎空闲后执行，所以定时器中的任务在设定的时间点不一定能够准时执行，定时器只是在指定时间点将任务添加到事件队列中;

注意:W3C在HTML标准中规定，定时器的定时时间不能小于4ms，如果是小于4ms，则默认为4ms。

浏览器渲染进程（Renderer Process）是**多线程**的，它负责页面的渲染、JavaScript 的执行、事件的处理以及网络请求等。

主要线程包括以下几个：

---

### 1. 🎨 GUI 渲染线程 (GUI Rendering Thread)

- **职责：** 负责渲染浏览器界面，解析 **HTML** 和 **CSS**，构建 **DOM 树** 和 **Render Tree**（渲染树）。它还负责页面的 **布局**（Layout/Reflow）和 **绘制**（Painting/Repaint）。
    
- **互斥性：** **GUI 渲染线程** 与 **JS 引擎线程** 是**互斥**的。当 **JS 引擎线程** 运行时，**GUI 渲染线程** 会被挂起（冻结），所有界面更新会被保存在一个队列中，直到 **JS 引擎线程** 空闲时才会立即执行。这是为了避免在 JS 修改 DOM 的过程中，渲染线程进行绘制，导致冲突和渲染结果不可预期。
    

---

### 2. ⚙️ JS 引擎线程 (JavaScript Engine Thread)

- **职责：** 也称为 JS 内核线程（例如 Chrome 的 V8 引擎），它负责解析和执行 **JavaScript 脚本** 程序。
    
- **特性：** 它是**单线程**的。在一个 Tab 页（即一个渲染进程）内，任何时候都只有一个 JS 线程在运行 JS 程序。
    
- **阻塞：** 由于其单线程特性和与 **GUI 渲染线程** 的互斥关系，如果 JS 执行时间过长，会阻塞页面的渲染和响应，导致页面卡顿或加载阻塞。
    

---

### 3. 🚨 事件触发线程 (Event Triggering Thread)

- **职责：** 归属于浏览器内核而非 JS 引擎，用于控制 **事件循环**（Event Loop）。
    
- **工作机制：** 当 JS 引擎执行异步代码（如 `setTimeout`、点击事件、AJAX 异步请求等）时，该线程会将对应的任务添加到待处理队列（**任务队列/消息队列**）中。当事件符合触发条件时（如定时器时间到、鼠标点击等），它将事件添加到队列队尾，等待 **JS 引擎线程** 空闲时进行处理。
    

---

### 4. 🌐 异步 HTTP 请求线程 (Asynchronous HTTP Request Thread)

- **职责：** 处理 **AJAX/Fetch** 等网络请求。当使用 `XMLHttpRequest` 或 `fetch` 发送网络请求时，该线程会执行请求。
    
- **工作机制：** 在请求发送后，该线程继续监听状态变化。当请求成功返回（`readyState` 变为 4 或请求完成）时，它会将对应的**回调函数**（例如 `onreadystatechange` 或 `then()` 中的代码）作为任务添加到 **事件队列** 中，等待 **JS 引擎线程** 执行。
    

---

### 5. 📦 定时器线程 (Timer Thread)

- **职责：** 负责处理 `setTimeout` 和 `setInterval` 等定时器的等待和触发。
    
- **工作机制：** 浏览器单独启动一个线程来计时，避免 JS 引擎的阻塞影响计时的准确性。当计时结束，它会将对应的**回调函数**作为一个任务添加到 **事件队列** 中，等待 **JS 引擎线程** 执行。
    

---

### 1. 经典或概念性的五种线程 (功能职责)

这张图描述的是**渲染进程（Renderer Process）**内部的协作，以及它如何将生成的数据交给**GPU 进程**上屏。

#### **第一阶段：主线程 (Main Thread) —— 这里的 "大管家"**

左侧的黄色区域是主线程，它承担了最繁重的逻辑处理工作。

- **职责范围**：如左侧红框所示，它负责 `1. 执行 JS 代码 (V8)`、`2. 解析 HTML/CSS`、`3. 样式计算、布局` 以及 `5. 事件循环`。
    
- **第 4 步 "绘制" (Paint)**：
    
    - **注意**：这里的“绘制”并不是真正把像素画到屏幕上，而是生成**绘制记录 (Paint Records)**。
        
    - 就好比主线程写了一张清单：“在 (x,y) 画一个红色的圆，在 (a,b) 写一行字”。
        
    - 生成完这个绘制列表后，主线程会将这些信息**提交 (Commit)** 给合成器线程。
        

#### **第二阶段：合成器线程 (Compositor Thread) —— 这里的 "调度员"**

中间的白色方块是合成器线程。它的核心目的是**不仅要画出来，还要画得快（流畅滚动）**。

- **接收数据**：它接收主线程提交过来的页面结构（层树 Layer Tree）和绘制列表。
    
- **分块 (Tiling)**：如果网页很长，一次画完太慢。合成器线程会将页面切分成很多小的**图块 (Tiles)**。
    
- **发送指令**：它根据当前视口（用户能看到的地方）及其附近区域，决定优先处理哪些图块，然后将这些图块的 **"绘制指令"** 发送给**光栅化线程**。
    

#### **第三阶段：光栅化线程 (Raster Thread) —— 这里的 "填色工"**

右侧的白色方块是光栅化线程（通常是一个线程池）。

- **光栅化 (Rasterization)**：这是将“矢量指令”（画个圆）转换成“位图数据”（一堆红色的像素点）的过程。
    
- **回传数据**：处理完成后，它将 **"绘制数据"**（即处理好的位图/纹理）反馈给合成器线程。
    
    - _注：在现代浏览器中，光栅化操作通常也会调用 GPU 加速（即 GPU Rasterization），虽然图里把它画在渲染进程框内，但实际运算可能发生在 GPU 硬件上。_
        

#### **第四阶段：GPU 进程 —— 最终上屏**

底部的 GPU 进程负责最后的展示。

- **生成绘制方块 (Draw Quad)**：当合成器线程拿到光栅化好的图块后，它会生成一种叫 "Draw Quad" 的命令，指明页面里哪个位置用哪张图块。
    
- **最终合成**：合成器线程将 Draw Quad 命令发送给 **GPU 进程**。
    
- **上屏**：GPU 进程执行 **"最终图层合成、一帧页面的绘制"**，调用 OpenGL/DirectX 等图形接口，将画面显示在显示器上。
    

---

### 2. 是否所有的绘制渲染都会依靠 GPU 进程？

**简短回答：在现代浏览器默认配置下，是的，绝大部分绘制严重依赖 GPU 进程。** 但存在一种“软件渲染”的降级方案。

#### **A. 硬件加速模式（默认，Hardware Acceleration）**

这是你图片中展示的模式。

- **主线程**：计算布局。
    
- **光栅化**：通常使用 **GPU** 来进行光栅化（GPU Rasterization）。
    
- **合成**：必须由 **GPU 进程** 完成。
    
- **原因**：GPU 处理图形运算（矩阵变换、像素填充）比 CPU 快得多，能极大提升滚动流畅度和动画性能（CSS 3D 变换等）。
    

#### **B. 软件渲染模式（降级，Software Fallback）**

如果用户的电脑显卡驱动太老、显卡硬件不支持、或者用户手动在浏览器设置里关闭了“硬件加速”，浏览器会进入“软件渲染模式”。

- **光栅化**：完全由 **CPU** 在渲染进程中计算出像素（非常慢）。
    
- **合成**：CPU 计算出最终的一张大图。
    
- **显示**：即使是软件渲染，最终的位图通常还是需要交给操作系统（如 Windows 的 DWM 或 macOS 的 WindowServer）来显示，这个过程**通常还是会经过 GPU 进程的一个“透传”**，或者直接写入系统显存。
    
- **局限**：这种模式下，复杂的 CSS 3D 动画、Canvas 或 WebGL 可能会变得非常卡顿甚至无法运行。
    

#### **总结**

虽然理论上 CPU 可以做所有事情（软件光栅化），但为了性能，现代浏览器（Chrome/Edge/Safari）的架构设计就是**以 GPU 进程为核心**进行最终合成的。你可以认为**正常的网页渲染流程是离不开 GPU 进程的**。

## 3. 🚀 CSS 样式利用 GPU 硬件加速是指什么？

**“CSS 样式利用 GPU 进行硬件加速”** 是指通过某些特定的 CSS 属性，将页面中变动的元素提升为一个**独立的图层 (Layer)**，从而让其后续的动画和变化直接交给**合成器线程**和 **GPU 进程**处理，避开主线程的重排和重绘。

### 关键机制：提升图层 (Layer Promotion)

当你在元素上使用以下 CSS 属性时，浏览器通常会将其提升为独立的图层：

1. **`transform: translateZ(0)`** 或 **`transform: translate3d(x, y, z)`**：这是最常用的技巧，欺骗浏览器为该元素创建一个 3D 渲染上下文，从而将其提升到独立图层。
    
2. **`will-change: property-name`**：明确告诉浏览器该元素将要改变，浏览器会提前进行优化（如提升图层）。
    
3. **`opacity`**：改变不透明度。
    
4. **`filter`**：使用滤镜效果。
    

### 为什么这比传统重绘更高效？

- **传统重绘 (Repaint)：** 改变颜色、背景色 → 主线程重新生成绘制记录 → 主线程将记录发给光栅化线程 → 光栅化线程处理。整个流程依然依赖主线程。
    
- **GPU 加速 (合成)：** 改变 `transform` 或 `opacity` → 元素是独立图层 → 变化只影响这个图层本身的位置或透明度，不影响其他图层 → **合成器线程** 直接修改该图层在屏幕上的**合成位置**或**透明度值**，然后发送给 **GPU 进程** → GPU 进程快速合成显示。
    

这个过程，我们称为**仅合成 (Compositor-Only) 动画**或 **Impl-Side Painting**。它完全避开了耗时的布局（重排）和绘制记录生成（重绘）步骤，性能极高。

### “不是说所有的绘制都依赖 GPU 加速吗？”

这是一个很好的疑问，需要区分**渲染阶段**和**加速对象**：

|**概念**|**含义**|**依赖**|**性能**|
|---|---|---|---|
|**基础绘制（Paint）**|主线程生成绘制记录，**绘制指令**。|**CPU**（主线程）|慢，涉及 JS 执行、DOM 操作。|
|**光栅化（Rasterization）**|将指令转为像素（位图）。|**GPU**（通过光栅化线程调用）|默认开启，快。|
|**合成（Compositing）**|移动、缩放、透明度变化等**图层操作**。|**GPU**（通过合成器线程调用）|极快，不占用主线程。|

因此，**所有的**最终**显示**都依赖 GPU 进程进行**光栅化和合成**是正确的（在硬件加速模式下）。但是，我们谈论 **“CSS 硬件加速”** 时，指的是通过**图层提升**让元素的变化**直接进入合成阶段**，从而跳过**主线程的绘制（Paint）和布局（Layout）**，让性能得到本质提升。

# 为什么重绘会占用主线程时间，他不是依靠合成器线程去修改的吗

这是一个非常好的问题，它触及了浏览器渲染优化的核心区别：**重绘 (Repaint/Paint)** 和 **合成 (Compositing)** 的区别。

## 🎨 重绘为什么占用主线程时间？

**重绘 (Repaint)** 占用主线程时间，因为它涉及**像素数据的生成**，而这部分初始工作是由主线程负责调度的，并且需要访问和操作 **DOM 树** 和 **样式信息**。

### 1. 触发主线程的“绘制记录”

重绘是指元素的**外观样式**发生了变化（例如改变了背景色、字体颜色），但**几何尺寸和位置没有变化**。

- **主线程职责：** 即使是颜色变化，浏览器也必须在**主线程**上重新生成该元素的**绘制记录 (Paint Records)**。这个记录本质上是一组矢量绘图指令，告诉浏览器：“请在这里画一个宽度 100px、高度 20px、颜色为红色的矩形。”
    
- **指令生成消耗：** 生成这些指令需要主线程访问 DOM 树和计算后的样式树（CSSOM），这是一个 **CPU 密集型**操作，自然会占用主线程时间。
    

### 2. 重绘的完整流程

重绘的完整流程依然需要主线程参与：

1. **主线程 (CPU)：** 发现样式改变，执行 **绘制 (Paint)**，重新生成受影响元素的绘制记录。
    
2. **主线程/光栅化线程 (CPU/GPU)：** 将这些绘制记录转换为实际的**像素位图**（光栅化）。这个过程虽然可以利用 GPU 加速，但任务的**调度**和**初始数据准备**仍从主线程开始。
    
3. **合成器线程 (GPU/CPU)：** 将新的像素位图整合到页面图层中。
    
4. **GPU 进程：** 显示最终结果。
    

因此，**重绘的开销主要在于第一步（生成绘制记录）和第二步（光栅化调度）**，这两步都严重依赖主线程。

---

## 🚀 合成（Compositing）为什么不占用主线程时间？

你之所以会认为重绘不占用主线程，是因为你可能将它与**“仅合成”动画**混淆了。

### 核心区别：图层的操作 vs 图层内容的修改

|**机制**|**触发的操作**|**核心处理者**|**是否占用主线程？**|
|---|---|---|---|
|**重绘 (Repaint)**|改变颜色、背景、阴影等**元素内容**|**主线程** (生成绘制记录)|**是**|
|**合成 (Compositing)**|改变 `transform`、`opacity` 等**图层属性**|**合成器线程**|**否**|

**合成器线程**的优势在于，它只处理**图层**级别的操作，例如：

- **移动** (`transform: translate`)
    
- **缩放** (`transform: scale`)
    
- **透明度** (`opacity`)
    

对于这些操作，合成器线程不需要知道图层内部的样式细节。它只需要知道图层的内容（像素位图）在哪里，然后直接修改这个图层的 **GPU 坐标** 或 **透明度值** 即可。它跳过了主线程的布局和绘制步骤，直接进入了高效的 **GPU 硬件加速**流程。

**总结：**

- **重绘** = 元素的**内容**变了，需要主线程重新生成绘制指令。
    
- **合成** = 元素的**位置/透明度**变了，合成器线程直接在 GPU 上操作图层，主线程无需干预。![[从浏览器架构理解JavaScript事件循环.png]]您提供的图片内容是**基本正确**的，但可能使用了**现代浏览器（如 Chromium 架构）**中更技术性或更细节的线程命名，与我之前回答中使用的**经典或概念性**命名略有不同。

### 2. 是否所有的绘制渲染都会依靠 GPU 进程？

**简短回答：在现代浏览器默认配置下，是的，绝大部分绘制严重依赖 GPU 进程。** 但存在一种“软件渲染”的降级方案。

#### **A. 硬件加速模式（默认，Hardware Acceleration）**

这是你图片中展示的模式。

- **主线程**：计算布局。
    
- **光栅化**：通常使用 **GPU** 来进行光栅化（GPU Rasterization）。
    
- **合成**：必须由 **GPU 进程** 完成。
    
- **原因**：GPU 处理图形运算（矩阵变换、像素填充）比 CPU 快得多，能极大提升滚动流畅度和动画性能（CSS 3D 变换等）。
    

#### **B. 软件渲染模式（降级，Software Fallback）**

如果用户的电脑显卡驱动太老、显卡硬件不支持、或者用户手动在浏览器设置里关闭了“硬件加速”，浏览器会进入“软件渲染模式”。

- **光栅化**：完全由 **CPU** 在渲染进程中计算出像素（非常慢）。
    
- **合成**：CPU 计算出最终的一张大图。
    
- **显示**：即使是软件渲染，最终的位图通常还是需要交给操作系统（如 Windows 的 DWM 或 macOS 的 WindowServer）来显示，这个过程**通常还是会经过 GPU 进程的一个“透传”**，或者直接写入系统显存。
    
- **局限**：这种模式下，复杂的 CSS 3D 动画、Canvas 或 WebGL 可能会变得非常卡顿甚至无法运行。
    

#### **总结**

虽然理论上 CPU 可以做所有事情（软件光栅化），但为了性能，现代浏览器（Chrome/Edge/Safari）的架构设计就是**以 GPU 进程为核心**进行最终合成的。你可以认为**正常的网页渲染流程是离不开 GPU 进程的**。

## 3. 🚀 CSS 样式利用 GPU 硬件加速是指什么？

**“CSS 样式利用 GPU 进行硬件加速”** 是指通过某些特定的 CSS 属性，将页面中变动的元素提升为一个**独立的图层 (Layer)**，从而让其后续的动画和变化直接交给**合成器线程**和 **GPU 进程**处理，避开主线程的重排和重绘。

### 关键机制：提升图层 (Layer Promotion)

当你在元素上使用以下 CSS 属性时，浏览器通常会将其提升为独立的图层：

1. **`transform: translateZ(0)`** 或 **`transform: translate3d(x, y, z)`**：这是最常用的技巧，欺骗浏览器为该元素创建一个 3D 渲染上下文，从而将其提升到独立图层。
    
2. **`will-change: property-name`**：明确告诉浏览器该元素将要改变，浏览器会提前进行优化（如提升图层）。
    
3. **`opacity`**：改变不透明度。
    
4. **`filter`**：使用滤镜效果。
    

### 为什么这比传统重绘更高效？

- **传统重绘 (Repaint)：** 改变颜色、背景色 → 主线程重新生成绘制记录 → 主线程将记录发给光栅化线程 → 光栅化线程处理。整个流程依然依赖主线程。
    
- **GPU 加速 (合成)：** 改变 `transform` 或 `opacity` → 元素是独立图层 → 变化只影响这个图层本身的位置或透明度，不影响其他图层 → **合成器线程** 直接修改该图层在屏幕上的**合成位置**或**透明度值**，然后发送给 **GPU 进程** → GPU 进程快速合成显示。
    

这个过程，我们称为**仅合成 (Compositor-Only) 动画**或 **Impl-Side Painting**。它完全避开了耗时的布局（重排）和绘制记录生成（重绘）步骤，性能极高。

### “不是说所有的绘制都依赖 GPU 加速吗？”

这是一个很好的疑问，需要区分**渲染阶段**和**加速对象**：

|**概念**|**含义**|**依赖**|**性能**|
|---|---|---|---|
|**基础绘制（Paint）**|主线程生成绘制记录，**绘制指令**。|**CPU**（主线程）|慢，涉及 JS 执行、DOM 操作。|
|**光栅化（Rasterization）**|将指令转为像素（位图）。|**GPU**（通过光栅化线程调用）|默认开启，快。|
|**合成（Compositing）**|移动、缩放、透明度变化等**图层操作**。|**GPU**（通过合成器线程调用）|极快，不占用主线程。|

因此，**所有的**最终**显示**都依赖 GPU 进程进行**光栅化和合成**是正确的（在硬件加速模式下）。但是，我们谈论 **“CSS 硬件加速”** 时，指的是通过**图层提升**让元素的变化**直接进入合成阶段**，从而跳过**主线程的绘制（Paint）和布局（Layout）**，让性能得到本质提升。

# 为什么重绘会占用主线程时间，他不是依靠合成器线程去修改的吗

这是一个非常好的问题，它触及了浏览器渲染优化的核心区别：**重绘 (Repaint/Paint)** 和 **合成 (Compositing)** 的区别。

---

## 🎨 重绘为什么占用主线程时间？

**重绘 (Repaint)** 占用主线程时间，因为它涉及**像素数据的生成**，而这部分初始工作是由主线程负责调度的，并且需要访问和操作 **DOM 树** 和 **样式信息**。

### 1. 触发主线程的“绘制记录”

重绘是指元素的**外观样式**发生了变化（例如改变了背景色、字体颜色），但**几何尺寸和位置没有变化**。

- **主线程职责：** 即使是颜色变化，浏览器也必须在**主线程**上重新生成该元素的**绘制记录 (Paint Records)**。这个记录本质上是一组矢量绘图指令，告诉浏览器：“请在这里画一个宽度 100px、高度 20px、颜色为红色的矩形。”
    
- **指令生成消耗：** 生成这些指令需要主线程访问 DOM 树和计算后的样式树（CSSOM），这是一个 **CPU 密集型**操作，自然会占用主线程时间。
    

### 2. 重绘的完整流程

重绘的完整流程依然需要主线程参与：

1. **主线程 (CPU)：** 发现样式改变，执行 **绘制 (Paint)**，重新生成受影响元素的绘制记录。
    
2. **主线程/光栅化线程 (CPU/GPU)：** 将这些绘制记录转换为实际的**像素位图**（光栅化）。这个过程虽然可以利用 GPU 加速，但任务的**调度**和**初始数据准备**仍从主线程开始。
    
3. **合成器线程 (GPU/CPU)：** 将新的像素位图整合到页面图层中。
    
4. **GPU 进程：** 显示最终结果。
    

因此，**重绘的开销主要在于第一步（生成绘制记录）和第二步（光栅化调度）**，这两步都严重依赖主线程。

---

## 🚀 合成（Compositing）为什么不占用主线程时间？

你之所以会认为重绘不占用主线程，是因为你可能将它与**“仅合成”动画**混淆了。

### 核心区别：图层的操作 vs 图层内容的修改

|**机制**|**触发的操作**|**核心处理者**|**是否占用主线程？**|
|---|---|---|---|
|**重绘 (Repaint)**|改变颜色、背景、阴影等**元素内容**|**主线程** (生成绘制记录)|**是**|
|**合成 (Compositing)**|改变 `transform`、`opacity` 等**图层属性**|**合成器线程**|**否**|

**合成器线程**的优势在于，它只处理**图层**级别的操作，例如：

- **移动** (`transform: translate`)
    
- **缩放** (`transform: scale`)
    
- **透明度** (`opacity`)
    

对于这些操作，合成器线程不需要知道图层内部的样式细节。它只需要知道图层的内容（像素位图）在哪里，然后直接修改这个图层的 **GPU 坐标** 或 **透明度值** 即可。它跳过了主线程的布局和绘制步骤，直接进入了高效的 **GPU 硬件加速**流程。

**总结：**

- **重绘** = 元素的**内容**变了，需要主线程重新生成绘制指令。
    
- **合成** = 元素的**位置/透明度**变了，合成器线程直接在 GPU 上操作图层，主线程无需干预。
