**CSRF攻击可以使用以下方法来防护:**
- **进行同源检测**，服务器根据http请求头中` origin` 或者` referer `信息来判断请求是否为允许访问的站点，从而对请求进行过滤。当origin或者referer信息都不存在的时候，直接阻止请求。这种方式的缺点是有些情况下referer可以被伪造，同时还会把搜索引擎的链接也给屏蔽了。所以一般网站会允许搜索引擎的页面请求,但是相应的页面请求这种请求方式也可能被攻击者给利用。(Referer字段会告诉服务器该网页是从哪个页面链接过来的)
- **使用CSRF Token进行验证**，服务器向用户返回一个随机数Token，当网站再次发起请求时，在请求参数中加入服务器端返回的 token，然后服务器对这个token进行验证。这种方法解决了使用cookie单一验证方式时，可能会被冒用的问题，但是这种方法存在一个缺点就是，我们需要给网站中的所有请求都添加上这个token，操作比较繁琐。还有一个问题是一般不会只有一台网站服务器，如果请求经过负载平衡转移到了其他的服务器，但是这个服务器的session中没有保留这个token 的话，就没有办法验证了。这种情况可以通过改变token 的构建方式来解决。
- **对Cookie进行双重验证**，服务器在用户访问网站页面时，向请求域名注入一个Cookie，内容为随机字符串，然后当用户再次向服务器发送请求的时候，从cookie 中取出这个字符串，添加到URL参数中，然后服务器通过对cookie 中的数据和参数中的数据进行比较，来进行验证。使用这种方式是利用了攻击者只能利用cookie，但是不能访问获取 cookie的特点。并且这种方法比CSRF Token的方法更加方便，并且不涉及到分布式访问的问题。这种方法的缺点是如果网站存在XSS漏洞的，那么这种方式会失效。同时这种方式不能做到子域名的隔离。
- **在设置cookie属性的时候设置Samesite**，限制cookie不能作为被第三方使用，从而可以避免被攻击者利用。Samesite一共有两种模式，一种是严格模式，在严格模式下cookie在任何情况下都不可能作为第三方Cookie使用，在宽松模式下，cookie可以被请求是GET请求，且会发生页面跳转的请求所使用.



以下是针对每种方法的示例：

1. 同源检测：

```javascript
// 服务器端代码（Node.js）
const allowedDomains = ['https://example.com', 'https://subdomain.example.com'];

app.use((req, res, next) => {
  const origin = req.headers.origin;
  const referer = req.headers.referer;

  if (origin && allowedDomains.includes(origin) || referer && allowedDomains.includes(referer)) {
    // 请求来自允许的域，继续处理请求
    next();
  } else {
    // 请求来自未授权的域，返回错误响应或跳转到错误页面
    res.status(403).send('Forbidden');
  }
});
```

上述示例中，服务器根据请求的 `origin` 或 `referer` 头部信息来判断请求是否来自允许访问的站点。如果请求来自未授权的域，可以返回适当的错误响应或进行重定向。

2. CSRF Token 验证：

```javascript
// 服务器端代码（Node.js）
const csrf = require('csurf');
const csrfProtection = csrf({ cookie: true });

app.use(csrfProtection);

// 在需要进行 CSRF 验证的请求中添加 CSRF Token
app.get('/form', (req, res) => {
  res.render('form', { csrfToken: req.csrfToken() });
});

app.post('/process', (req, res) => {
  // 验证 CSRF Token
  if (req.body.csrfToken === req.csrfToken()) {
    // CSRF Token 验证通过，继续处理请求
    // ...
  } else {
    // CSRF Token 验证失败，返回错误响应
    res.status(403).send('CSRF Token Validation Failed');
  }
});
```

在上述示例中，服务器使用 `csurf` 中间件生成和验证 CSRF Token。在表单渲染时，将 CSRF Token 添加到表单中，然后在处理提交请求时，验证请求参数中的 CSRF Token。

3. 双重验证：

```javascript
// 服务器端代码（Node.js）
const randomString = require('randomstring');

app.use((req, res, next) => {
  const csrfCookieName = 'csrfToken';
  const csrfQueryParam = 'csrfToken';

  if (req.cookies[csrfCookieName] && req.cookies[csrfCookieName] === req.query[csrfQueryParam]) {
    // 双重验证通过，继续处理请求
    next();
  } else {
    // 双重验证失败，返回错误响应
    res.status(403).send('Double Validation Failed');
  }
});

app.get('/page', (req, res) => {
  const csrfToken = randomString.generate(16);
  res.cookie('csrfToken', csrfToken);
  res.render('page', { csrfToken: csrfToken });
});
```

在上述示例中，服务器在用户访问页面时，在 Cookie 中注入一个随机字符串作为 CSRF Token，并将其添加到页面的参数中。然后在请求中，通过比较 Cookie 中的 CSRF Token 和请求参数中的 CSRF Token 进行双重验证。

4. 设置 SameSite 属性：

```javascript
// 服务器端代码（Node.js）
app.use((req, res, next) => {
  res.cookie('cookieName', 'cookieValue', { sameSite: 'Strict' });
  next();
});
```

上述示例中，通过设置 `sameSite` 属性为 `'Strict'`，将 Cookie 的 SameSite 属性设置为严格模式，限制其仅在同一站点下使用。

请注意，上述示例中的代码仅作为演示，实际应用中需要根据具体的服务器端框架和需求进行适当的调整和配置。此外，综合使用多个防护措施可以提高应用程序的安全性。


## cookie 的属性samesite，要让cookie跨域怎么做
属性 `SameSite` 是用于控制 Cookie 在跨站点请求时是否发送的一种安全机制。默认情况下，Cookie 是不会跨域发送的，以防止跨站点请求伪造（CSRF）攻击。

如果你想要允许某个 Cookie 在跨域请求中发送，可以将 `SameSite` 属性设置为 `"None"`，并结合 `Secure` 属性一起使用。这样，该 Cookie 将只在使用安全连接（HTTPS）时才会被发送。

以下是设置 `SameSite` 和 `Secure` 属性的示例代码（使用 JavaScript）：

```javascript
document.cookie = "cookieName=cookieValue; SameSite=None; Secure";
```

上述代码将名为 `cookieName`，值为 `cookieValue` 的 Cookie 设置为可以在跨域请求中发送的 Cookie。

请注意，设置 `SameSite=None` 和 `Secure` 属性的同时，需要确保你的网站正在使用 HTTPS 连接。这是因为 `Secure` 属性要求连接是安全的，否则浏览器将不会发送该 Cookie。

另外，需要注意的是，某些旧版本的浏览器可能不支持 `SameSite=None` 和 `Secure` 属性。在实际使用时，建议进行兼容性测试，并根据需要进行适当的处理。

总结起来，要让 Cookie 能够在跨域请求中发送，需要设置以下两个属性：
1. `SameSite=None`：表示该 Cookie 可以在跨域请求中发送。
2. `Secure`：要求连接是安全的（HTTPS）。

请注意，跨域 Cookie 的使用需要谨慎，确保你了解其中的安全风险，并只在必要的情况下使用。
