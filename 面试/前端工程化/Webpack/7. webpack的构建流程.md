## version 1 

	Webpack的运行流程是一个串行的过程，从启动到结束会依次执行以下流程:
	1．初始化参数:从配置文件和Shell语句中读取与合并参数，得出最终的参数;
	2．开始编译:用上一步得到的参数初始化Compiler对象，加载所有配置的插件，执行对象的run方法开始执行编译;
	3．确定入口:根据配置中的entry 找出所有的入口文件;
	4．编译模块:从入口文件出发，调用所有配置的Loader对模块进行翻译，再找出该模块依赖的模块，再递归本步骤直到所有入口依赖的文件都经过了本步骤的处理;
	5.完成模块编译:在经过第4步使用Loader翻译完所有模块后，得到了每个模块被翻译后的最终内容以及它们之间的依赖关系;
	6．输出资源:根据入口和模块之间的依赖关系，组装成一个个包含多个模块的Chunk，再把每个Chunk转换成一个单独的文件加入到输出列表，这步是可以修改输出内容的最后机会;
	7．输出完成:在确定好输出内容后，根据配置确定输出的路径和文件名，把文件内容写入到文件系统。
	在以上过程中，Webpack 会在特定的时间点广播出特定的事件，插件在监听到感兴趣的事件后会执行特定的逻辑，并且插件可以调用Webpack提供的API改变Webpack的运行结果。


### 例子
假设我们有一个简单的 Webpack 项目，包含一个入口文件 `index.js` 和一个依赖文件 `module.js`，其中 `index.js` 依赖于 `module.js`，并且需要进行 ES6 转换和样式加载。那么整个 Webpack 的运行流程如下：

1. 初始化参数：从配置文件 `webpack.config.js` 中读取参数，并与命令行参数进行合并，得出最终的参数。
   以下是一个示例，演示如何从 `webpack.config.js` 配置文件和命令行参数中读取参数，并将它们合并为最终的参数：

```javascript
const path = require('path');
const webpack = require('webpack');
const yargs = require('yargs');

// 从配置文件中读取参数
const configPath = path.resolve(__dirname, 'webpack.config.js');
const config = require(configPath);

// 从命令行参数中读取参数
const argv = yargs.argv;
const commandLineArgs = {
  mode: argv.mode || 'development',
  outputDir: argv.outputDir || 'dist',
};

// 合并参数
const finalConfig = {
  ...config,
  mode: commandLineArgs.mode,
  output: {
    ...config.output,
    path: path.resolve(__dirname, commandLineArgs.outputDir),
  },
};

// 使用最终的参数来构建 webpack 配置
webpack(finalConfig, (err, stats) => {
  if (err) {
    console.error(err);
  } else {
    console.log(stats.toString({ colors: true }));
  }
});
```

在这个示例中，假设我们有一个名为 `webpack.config.js` 的配置文件，其中包含一些 webpack 的配置选项，如 `entry`、`output` 等。通过 `require` 函数将配置文件加载为一个对象。

我们还使用了 `yargs` 库来解析命令行参数。在命令行中，可以使用 `--mode` 和 `--outputDir` 参数来覆盖默认的模式和输出目录。

首先，我们读取配置文件中的参数，并将它们存储在 `config` 对象中。然后，使用 `yargs.argv` 读取命令行参数，并将它们存储在 `commandLineArgs` 对象中。

接下来，我们使用对象展开运算符 (`...`) 将配置文件中的参数和命令行参数合并到 `finalConfig` 对象中。我们还根据命令行参数更新 `output.path`，以确保输出目录路径正确。

最后，我们使用最终的参数 `finalConfig` 来构建 webpack 配置，并进行构建操作。在构建完成后，我们可以根据需要处理构建结果。

这个示例展示了如何从配置文件和命令行参数中读取参数，并将它们合并为最终的参数。你可以根据自己的需求和项目的配置文件结构进行相应的修改和扩展。

2. 开始编译：用上一步得到的参数初始化 `Compiler` 对象，加载所有配置的插件，执行对象的 `run` 方法开始执行编译。
   
   
在 webpack 中，可以使用上一步中得到的参数来初始化 `Compiler` 对象，并执行编译过程。以下是一个示例：

```javascript
const webpack = require('webpack');

// 使用上一步得到的参数初始化 Compiler 对象
const compiler = webpack(finalConfig);

// 加载所有配置的插件
compiler.hooks.afterPlugins.tap('AfterPlugins', () => {
  // 在这里可以执行其他插件相关的操作
});

// 执行编译
compiler.run((err, stats) => {
  if (err) {
    console.error(err);
  } else {
    console.log(stats.toString({ colors: true }));
  }
});
```

在这个示例中，我们使用 `finalConfig` 对象（上一步中得到的最终参数）来初始化 `Compiler` 对象。`Compiler` 对象是 webpack 的核心编译器，负责管理整个编译过程。

然后，我们可以通过 `compiler.hooks.afterPlugins` 钩子来加载所有配置的插件。这个钩子会在插件加载完成后被触发，你可以在其中执行其他插件相关的操作。

最后，我们调用 `compiler.run` 方法来执行编译过程。在编译完成后，`run` 方法的回调函数中会接收到一个 `stats` 对象，它包含有关编译过程的统计信息。我们可以使用 `toString` 方法将统计信息以彩色的形式打印到控制台。

请注意，上述示例中的代码片段仅涵盖了主要的步骤，并没有包括完整的 webpack 配置和插件的加载过程。根据你的具体需求和项目的配置，你可能需要进行更多的配置和插件加载操作。

3. 确定入口：根据配置中的 `entry` 找出所有的入口文件，我们这里只有一个入口文件 `index.js`。

根据配置中的 `entry`，可以确定 webpack 的入口文件。在这个示例中，我们假设配置文件中只有一个入口文件 `index.js`。

```javascript
const path = require('path');
const webpack = require('webpack');

// 从配置文件中读取参数
const configPath = path.resolve(__dirname, 'webpack.config.js');
const config = require(configPath);

// 获取入口文件

// 确定入口文件路径
const entryPath = path.resolve(__dirname, entry);

// 使用入口文件路径来构建 webpack 配置

  ...config,
  entry: entryPath,
};

// 创建 Compiler 对象并执行编译

compiler.run((err, stats) => {
  if (err) {
    console.error(err);
  } else {
    console.log(stats.toString({ colors: true }));
  }

```

在这个示例中，我们假设 `webpack.config.js` 配置文件中有一个 `entry` 属性，其值为入口文件的相对路径（例如 `index.js`）。

首先，我们从配置文件中读取 `entry` 参数，并将其存储在 `entry` 变量中。

接下来，我们使用 `path.resolve` 方法将入口文件的相对路径解析为绝对路径，并将其存储在 `entryPath` 变量中。

然后，我们将入口文件路径更新到 `finalConfig` 对象的 `entry` 属性中。

最后，我们使用更新后的 `finalConfig` 对象来创建 `Compiler` 对象，并执行编译过程。

请注意，这只是一个示例，假设只有一个入口文件。实际上，webpack 支持多个入口文件，并且可以通过对象或数组的形式进行配置。你可以根据你的实际需求在配置文件中定义多个入口文件，并相应地调整代码来确定所有的入口文件。



4. 编译模块：从入口文件 `index.js` 出发，调用所有配置的 `Loader` 对模块进行翻译，再找出该模块依赖的模块，即 `module.js`，再递归本步骤直到所有入口依赖的文件都经过了本步骤的处理。在这里，`babel-loader` 会对 `index.js` 和 `module.js` 进行 ES6 转换，`style-loader` 和 `css-loader` 会对 `index.js` 进行样式加载。
在 webpack 中，可以通过配置 `Loader` 来对模块进行翻译和处理。在你的示例中，`babel-loader` 用于对 `index.js` 和 `module.js` 进行 ES6 转换，`style-loader` 和 `css-loader` 用于对 `index.js` 进行样式加载。以下是一个示例：

```javascript
const path = require('path');
const webpack = require('webpack');

// 从配置文件中读取参数
const configPath = path.resolve(__dirname, 'webpack.config.js');
const config = require(configPath);

// 获取入口文件
const entry = config.entry;

// 确定入口文件路径
const entryPath = path.resolve(__dirname, entry);

// 使用入口文件路径来构建 webpack 配置
const finalConfig = {
  ...config,
  entry: entryPath,
};

// 创建 Compiler 对象并执行编译
const compiler = webpack(finalConfig);
compiler.run((err, stats) => {
  if (err) {
    console.error(err);
  } else {
    console.log(stats.toString({ colors: true }));
  }
});
```

在上述示例中，我们假设 `webpack.config.js` 配置文件中已经配置了相应的 `Loader`，包括 `babel-loader`、`style-loader` 和 `css-loader`。

当执行编译时，webpack 会从入口文件 `index.js` 开始，根据配置文件中的 `Loader` 进行模块的翻译和处理。

对于 ES6 转换，我们可以在配置文件中添加以下配置：

```javascript
module.exports = {
  // ...
  module: {
    rules: [
      {
        test: /\.js$/, // 匹配以 .js 结尾的文件
        exclude: /node_modules/, // 排除 node_modules 目录
        use: {
          loader: 'babel-loader',
          options: {
            presets: ['@babel/preset-env'], // 使用 @babel/preset-env 进行转换
          },
        },
      },
    ],
  },
  // ...
};
```

对于样式加载，我们可以在配置文件中添加以下配置：

```javascript
module.exports = {
  // ...
  module: {
    rules: [
      {
        test: /\.css$/, // 匹配以 .css 结尾的文件
        use: ['style-loader', 'css-loader'], // 应用 style-loader 和 css-loader
      },
    ],
  },
  // ...
};
```

通过配置适当的 `test`、`exclude` 和 `use`，可以根据文件的类型和路径匹配相应的 `Loader` 进行处理。

请注意，在配置文件中可以定义多个 `Loader` 规则，用于处理不同类型的文件。你可以根据实际需求添加和配置适当的 `Loader` 来处理模块的翻译和加载。



5. 完成模块编译：在经过第4步使用 `Loader` 翻译完所有模块后，得到了每个模块被翻译后的最终内容以及它们之间的依赖关系。
在 webpack 中，经过第 4 步使用 `Loader` 翻译完所有模块后，你可以得到每个模块被翻译后的最终内容以及它们之间的依赖关系。这些信息可以通过 webpack 的编译结果对象（`stats`）来获取。

以下是一个示例，展示如何获取模块的最终内容和依赖关系：

```javascript
const path = require('path');
const webpack = require('webpack');

// 从配置文件中读取参数
const configPath = path.resolve(__dirname, 'webpack.config.js');
const config = require(configPath);

// 获取入口文件
const entry = config.entry;

// 确定入口文件路径
const entryPath = path.resolve(__dirname, entry);

// 使用入口文件路径来构建 webpack 配置
const finalConfig = {
  ...config,
  entry: entryPath,
};

// 创建 Compiler 对象并执行编译
const compiler = webpack(finalConfig);
compiler.run((err, stats) => {
  if (err) {
    console.error(err);
  } else {
    const modules = stats.toJson().modules;

    // 遍历每个模块
    modules.forEach((module) => {
      // 获取模块的最终内容
      const transformedCode = module.source;

      // 获取模块的依赖关系
      const dependencies = module.dependencies;

      console.log('Module:', module.name);
      console.log('Transformed Code:', transformedCode);
      console.log('Dependencies:', dependencies);
      console.log('----------------------');
    });
  }
});
```

在上述示例中，我们获取了编译结果对象 `stats`，并通过 `stats.toJson().modules` 获取了所有模块的信息。

然后，我们遍历每个模块，通过 `module.source` 获取模块的最终内容，通过 `module.dependencies` 获取模块的依赖关系。

你可以根据需要进一步处理模块的最终内容和依赖关系，例如输出到文件、进行进一步的处理等。

请注意，`stats` 对象提供了丰富的信息，除了模块的最终内容和依赖关系，还包括编译时间、编译警告、错误等。你可以根据实际需求，进一步探索和利用 `stats` 对象中的其他属性和方法。



6. 输出资源：根据入口和模块之间的依赖关系，组装成一个个包含多个模块的 `Chunk`，即将 `index.js` 和 `module.js` 打包成一个 `Chunk`，再把每个 `Chunk` 转换成一个单独的文件加入到输出列表，这步是可以修改输出内容的最后机会。在这里，我们得到了一个名为 `bundle.js` 的文件，其中包含了经过编译后的 `index.js` 和 `module.js`。
在 webpack 中，根据入口和模块之间的依赖关系，可以将它们组装成一个个包含多个模块的 `Chunk`，然后将每个 `Chunk` 转换成一个单独的文件，并将其加入到输出列表。这样，你可以得到一个名为 `bundle.js` 的文件，其中包含了经过编译后的 `index.js` 和 `module.js`。

以下是一个示例，展示如何配置 webpack 来实现输出资源的处理：

```javascript
const path = require('path');
const webpack = require('webpack');

// 从配置文件中读取参数
const configPath = path.resolve(__dirname, 'webpack.config.js');
const config = require(configPath);

// 获取入口文件
const entry = config.entry;

// 确定入口文件路径
const entryPath = path.resolve(__dirname, entry);

// 使用入口文件路径来构建 webpack 配置
const finalConfig = {
  ...config,
  entry: entryPath,
  output: {
    filename: 'bundle.js', // 输出文件名为 bundle.js
    path: path.resolve(__dirname, 'dist'), // 输出路径为 dist 目录
  },
};

// 创建 Compiler 对象并执行编译
const compiler = webpack(finalConfig);
compiler.run((err, stats) => {
  if (err) {
    console.error(err);
  } else {
    console.log(stats.toString({ colors: true }));
  }
});
```

在上述示例中，我们通过配置 `output` 属性来指定输出文件的名称和路径。在这里，我们将输出文件名设置为 `bundle.js`，输出路径设置为 `dist` 目录（需要事先创建该目录）。

当执行编译时，webpack 会根据入口和模块之间的依赖关系，将它们组装成 `Chunk`，然后将每个 `Chunk` 转换成一个单独的文件，并将其加入到输出列表中。在最终的输出结果中，你将得到一个名为 `bundle.js` 的文件，其中包含了经过编译后的 `index.js` 和 `module.js`。

请注意，输出文件的名称和路径可以根据你的实际需求进行配置。你可以根据需要修改输出文件名、输出路径以及其他相关的输出配置，以满足你的项目需求。



7. 输出完成：在确定好输出内容后，根据配置确定输出的路径和文件名，把文件内容写入到文件系统。在这里，我们将 `bundle.js` 输出到 `dist` 目录下。

在以上过程中，Webpack 会在特定的时间点广播出特定的事件，插件在监听到感兴趣的事件后会执行特定的逻辑，并且插件可以调用Webpack提供的API改变Webpack的运行结果。例如，`html-webpack-plugin` 插件会监听到 `emit` 事件，然后根据模板生成 HTML 文件，并将打包后的 JS 自动注入到 HTML 文件中。

在前端面试中，Webpack 的打包流程是一个高频考点。面试官不仅想听“转换代码”，更想听到你对**事件驱动架构（Tapable）**、**AST（抽象语法树）解析**以及**依赖图谱构建**的深度理解。

我们可以将 Webpack 的打包流程比作一条**自动化的流水线**，将其拆解为以下五个核心阶段：

---

### 1. 初始化阶段 (Initialization)

当你输入 `npm run build` 时，程序首先进入准备状态。

- **合并配置参数**：Webpack 会读取你的 `webpack.config.js`，并将其与 Shell 命令中的参数（如 `--mode=production`）进行合并，生成最终的 **Options** 对象。
    
- **创建 Compiler 对象**：Webpack 根据配置初始化 `Compiler` 对象。这个对象在整个构建生命周期中是**唯一的**，它包含了完整的 Webpack 环境配置。
    
- **挂载插件 (Plugins)**：Webpack 会遍历配置中的 `plugins` 数组，执行插件的 `apply` 方法。此时，插件开始监听 Webpack 生命周期中的各个钩子（Hooks）。
    

### 2. 构建准备阶段 (Preparation)

- **确定入口 (Entry)**：根据配置中的 `entry` 找到所有的入口文件。
    
- **创建 Compilation 对象**：Compiler 调用 `newCompilation` 方法创建一个 `Compilation` 对象。
    
    > **面试加分点**：区别于 Compiler（代表整个生命周期），`Compilation` 仅代表**当前的一次资源构建**。在 watch 模式下，每次文件修改都会创建一个新的 Compilation。
    

### 3. 编译模块阶段 (Module Build) - **核心环节**

这是 Webpack 最繁忙的阶段，它会递归地从入口开始“顺藤摸瓜”。

1. **调用 Loader 转换资源**：Webpack 默认只认识 JS 和 JSON。当遇到 `.vue`、`.scss` 或 `.png` 时，会根据 `module.rules` 找到对应的 Loader 进行转译。
    
2. **解析为 AST**：通过 `acorn` 解析器将转换后的 JS 代码转为 **抽象语法树 (AST)**。
    
3. **遍历 AST 并搜集依赖**：从 AST 中找到 `import`、`require()` 或 `define` 等语句。
    
4. **递归构建**：对这些依赖模块重复上述步骤（递归），直到所有的文件都经过了 Loader 处理并被解析完毕。
    

### 4. 完成编译与封装阶段 (Seal & Optimization)

所有模块处理完后，Webpack 开始对这些“零件”进行组装。

- **构建依赖图谱**：Webpack 内部会生成一个完整的 **Module Graph**，明确模块间的引用关系。
    
- **封装 Chunk**：Webpack 会根据入口和配置（如 `splitChunks`）将多个 Module 组合成一个个 **Chunk**（代码块）。
    
- **优化操作**：在这个阶段，Webpack 会进行 Tree Shaking（剔除死代码）、代码压缩、合并等优化工作。
    
- **生成 Asset**：将每个 Chunk 转换成一个单独的文件（Asset），此时文件内容已经确定，只等写入磁盘。
    

### 5. 输出阶段 (Emit)

- **写入文件系统**：根据配置中的 `output`（path 和 filename），Webpack 调用 Node.js 的 `fs` 模块，将内存中的 Asset 内容写入到本地磁盘（通常是 `dist` 目录）。
    
- **完成收尾**：触发 `done` 钩子，控制台打印出构建报告（如文件大小、耗时等）。
    

---

### 面试官可能会追问的深度细节：

|**关键概念**|**理解要点**|
|---|---|
|**Tapable**|Webpack 的核心骨架，类似于 NodeJS 的 EventEmitter，负责管理各种 Hooks 的发布与订阅。|
|**Loader vs Plugin**|**Loader** 是翻译官（作用于文件转换）；**Plugin** 是干预者（作用于整个构建周期，能修改输出结果）。|
|**Chunk vs Bundle**|**Chunk** 是过程中的代码块（模块聚合体）；**Bundle** 是最终输出到浏览器运行的文件。|

### 第一部分：Webpack 全链路深度解析 (源码级流程)

Webpack 本质上是一个事件流机制。面试时，建议用 **Hook（钩子）** 的流转来串联整个过程。

#### 1. 初始化与启动 (Init)

- **启动入口**：执行命令后，`webpack-cli` 会解析参数，读取 `webpack.config.js`。
    
- **配置合并**：使用 `webpack-merge` 策略，将 CLI 参数、默认配置、用户配置合并成最终的 `options`。
    
- **实例化 Compiler**：这是 Webpack 的**总指挥**。`Compiler` 类继承自 `Tapable`，它是单例的，保存了完整的配置环境。
    
- **加载插件**：遍历 `plugins` 数组，调用每个插件的 `apply(compiler)` 方法。插件此时开始监听 Compiler 的各种生命周期钩子（如 `entryOption`, `run`, `done`）。
    

#### 2. 编译启动 (Run)

- **Hooks.run**：Compiler 开始运行，触发 `run` 钩子。
    
- **Compilation 创建**：Compiler 触发 `compile` 钩子，并创建 **`Compilation`** 对象。
    
    - _重点_：`Compilation` 是**本次构建**的核心大脑，包含了当前的模块资源、编译生成资源、变化的文件等。每当检测到文件变化，都会创建一个新的 Compilation。
        

#### 3. 模块构建 (Make) —— _递归核心_

这是最耗时的环节，由 `Compilation` 的 `make` 钩子触发：

1. **Entry 寻找**：根据 `entry` 配置找到入口文件。
    
2. **Module Factory**：调用 `NormalModuleFactory` 创建一个模块实例。
    
3. **Loader 处理**：即 **Run Loaders**。找到该文件类型匹配的所有 Loaders，对源码进行转换（详见下文）。
    
4. **AST 解析**：使用 `acorn` 将 Loader 处理后的 JS 字符串解析为 **AST（抽象语法树）**。
    
5. **依赖收集**：遍历 AST，寻找 `import` / `require` 语句。
    
    - 如果是 ESM (`import`)，标记为 `HarmonyImportDependency`。
        
    - 如果是 CJS (`require`)，标记为 `CommonJsRequireDependency`。
        
6. **递归处理**：将收集到的依赖加入构建队列，重复上述 Step 2-5，直到所有文件处理完毕。
    

#### 4. 封装与优化 (Seal)

此时所有模块的翻译和依赖关系已建立：

- **构建 Chunk**：根据入口（Entry）和动态引入（Dynamic Import），将 Module 组装成 **Chunk**。
    
- **生成 Hash**：计算 Compilation 和 Chunk 的 Hash 值（用于缓存控制）。
    
- **执行优化**：触发 `optimize` 系列钩子。此时会进行 **Tree Shaking**、代码压缩（Minification）、ModuleId/ChunkId 的生成。
    

#### 5. 输出 (Emit)

- **生成 Assets**：将 Chunk 转换成最终输出的文件名和内容（字符串/Buffer），存放在 `compilation.assets` 中。
    
- **Hooks.emit**：**这是修改输出内容的最后机会**。很多插件（如 `html-webpack-plugin`）就是在这里将生成的 JS 插入到 HTML 中的。
    
- **写入磁盘**：Webpack 调用 Node.js 的文件系统，将 `assets` 内容写入 `output.path` 目录。
    
- **Hooks.done**：构建完成，打印统计信息。

### 第二部分：Loader 是如何被调用的？ (机制详解)

面试中常问：“为什么 Loader 是从右向左执行的？”

#### 1. 链式调用与函数组合

在 Webpack 配置中，use: ['style-loader', 'css-loader', 'sass-loader']。

Loader 本质上是一个导出函数的 JS 模块。Webpack 使用 loader-runner 库来执行它们。执行顺序遵循 函数组合 (Function Composition) 原理：

$$result = style(css(sass(source)))$$

#### 2. 双阶段执行：Pitching & Normal

Loader 的执行实际上分为两个阶段：**Pitching Phase**（从左到右）和 **Normal Phase**（从右到左）。

- Pitching 阶段 (Capture)：
    
    Webpack 先从左到右遍历 Loader 的 pitch 方法。
    
    style-loader.pitch -> css-loader.pitch -> sass-loader.pitch
    
    - _作用_：允许 Loader 在执行前利用元数据做拦截。如果某个 Loader 的 `pitch` 返回了结果，**后续的 Loader 将被跳过**，直接开始反向执行 Normal 阶段。
        
- Normal 阶段 (Bubble)：
    
    如果没有被拦截，读取文件内容，然后从右到左传递内容。
    
    sass-loader(source) -> 转换成 CSS -> css-loader(css) -> 处理 @import/url() -> style-loader(js) -> 插入 style 标签脚本。
    

#### 3. 执行细节

- **输入输出**：第一个执行的 Loader 接收源文件内容，后续 Loader 接收上一个 Loader 返回的字符串或 Buffer。
    
- **上下文**：Loader 运行时拥有一个 `this` 上下文（LoaderContext），里面包含 `this.async()`（用于异步转换）、`this.addDependency()`（用于添加文件监听）等方法。

### 第三部分：Tree Shaking 的实现原理

Tree Shaking（摇树优化）旨在移除 JavaScript 上下文中的死代码（Dead Code）。

#### 1. 前置条件：ES6 Modules (ESM)

Tree Shaking **必须**基于 ESM (`import/export`)。

- **原因**：ESM 是**静态分析**的，编译时就能确定模块的依赖关系。而 CommonJS (`require`) 是动态的，运行时才确定，无法进行静态剔除。
    

#### 2. 工作流程 (Mark & Sweep)

这个过程主要发生在 **Seal** 阶段和 **Terser/Uglify** 压缩阶段。

- 第一步：标记 (Make 阶段)
    
    Webpack 在遍历 AST 收集依赖时，会分析每个模块的 export 变量。它会记录哪些 export 被其他模块 import 了。
    
- 第二步：提炼 (Seal 阶段)
    
    Webpack 会利用 usedExports 配置。对于没有被用到的 export，Webpack 会在生成的代码中将其标记为 "unused harmony export"。
    
    - _结果_：代码还在 bundle 里，但没有导出引用。
        
- 第三步：剔除 (Minimizer 阶段)
    
    这是最关键的一步。通常由压缩插件（如 TerserWebpackPlugin）完成。Terser 扫描代码，发现变量声明了但未被引用（且没有副作用），就会直接将其从最终代码中删除。
    

#### 3. “副作用”难题 (Side Effects)

这是面试的高频坑点。

- **问题**：如果一个文件只是 `import './style.css'`，它没有导出任何东西，Tree Shaking 可能会误判将其删掉。或者一个 Polyfill 修改了全局 window 对象，这叫**副作用**。
    
- **解决**：在 `package.json` 中配置 `"sideEffects": ["*.css"]` 或 `false`。
    
    - `"sideEffects": false`：告诉 Webpack，我的所有代码都没有副作用，如果一个模块被引入但未被使用，**可以直接安全地跳过整个模块的导入**，不打包它。
