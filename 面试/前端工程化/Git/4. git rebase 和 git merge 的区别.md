### 4. git rebase 和 git merge 的区别

git merge 和 git rebase 都是用于分支合并，关键**在** **commit 记录的处理上不同**：

- git merge 会新建一个新的 commit 对象，然后两个分支以前的 commit 记录都指向这个新 commit 记录。这种方法会保留之前每个分支的 commit 历史。
- git rebase 会先找到两个分支的第一个共同的 commit 祖先记录，然后将提取当前分支这之后的所有 commit 记录，然后将这个 commit 记录添加到目标分支的最新提交后面。经过这个合并后，两个分支合并后的 commit 记录就变为了线性的记录了。

假设我们有一个 Git 仓库，其中包含两个分支：`feature` 分支和 `master` 分支。现在我们在 `feature` 分支上进行了一些提交。

1. 使用 `git merge master`：

   ```plaintext
   git checkout feature  # 切换到 feature 分支
   git merge master      # 将 master 分支合并到 feature 分支
   ```

   在这种情况下，Git 会将 `master` 分支的最新提交合并到 `feature` 分支中，形成一个新的合并提交。这个合并提交将包含两个分支的更改，并将它们整合在一起。这样，`feature` 分支将包含 `master` 分支的最新更改，但同时也保留了 `feature` 分支自己的提交历史。

   ```
   ──●──●──●──●──●──●──M─ (feature)
     /            /
   ──A──B──C──D──E─ (master)
   ```

   在上面的示例中，`A`、`B`、`C`、`D` 和 `E` 是 `master` 分支上的提交，`M` 是合并提交。

2. 使用 `git rebase master`：

   ```plaintext
   git checkout feature  # 切换到 feature 分支
   git rebase master     # 将 master 分支的更改应用到 feature 分支上
   ```

   在这种情况下，Git 会将 `feature` 分支上的提交暂时保存，然后将 `master` 分支的最新更改应用到 `feature` 分支上。这将在 `feature` 分支的每个提交之前插入 `master` 分支的更改。最后，`feature` 分支将包含 `master` 分支的最新更改，并且提交历史将成为线性结构。

   ```
   ──●──●──●──●──●──●──A'─B'─C'─D'─E'─ (feature)
     /            /
   ──A──B──C──D──E─ (master)
   ```

   在上面的示例中，`A'`、`B'`、`C'`、`D'` 和 `E'` 是应用到 `feature` 分支上的 `master` 分支的更改。

总结：
- `git merge` 会创建一个新的合并提交，将两个分支的更改整合在一起。
- `git rebase` 会将一个分支的更改应用到另一个分支上，并重写提交历史，使其成为线性结构。

通常情况下，如果你希望保留分支历史的完整性并创建明确的合并点，你可以选择使用 `git merge`。而如果你希望保持提交历史的线性结构并使其更加清晰，你可以选择使用 `git rebase`。具体选择哪种方法取决于个人或团队的偏好以及特定的项目需求。
