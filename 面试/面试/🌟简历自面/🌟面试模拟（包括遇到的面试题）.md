[[项目开发的流程]]
交互-设计-前后端开发-联调-提测-验收-新需求

自己的回答：
- 一般由产品经理跟对客户的需求进行分析然后整理成项目需求
- 再交给美工组，先由交互组根据项目需求设计页面的的逻辑功能，再交给设计组进行样式上面的设计，最后生成原型图交给开发组进行开发
- 开发之前开个会议说明本次迭代需要完成的需求，分析需求的可行度，对开发的内容进行评测，分析一下开发完成需要的时间，对需求的开发进行人员的分配，然后开启的需求功能的开发。
- 前后端都写好需求代码之后就进行联调，
	- 但如果在前端代码写好后，后端的接口还没有写好，就可以自己在mock上写对应的接口，比如我要发起get请求，请求数据，就根据原型图逻辑自己写一个json文件，等到后接口写完后再修改字段和部分逻辑。
	- 如果开发过程中对原型图不理解或者功能无法实现就在微信群里跟项目经理讨论
	- 开发过程中遇到的问题也要跟后端讨论，
	- 联调完后就可以先对功能进行自测。
- 然后提交给测试组进行测试，
- 然后交给客户进行验收，
- 然后开启新一轮的迭代需求的开发。

```js

function debounce(func, delay) {
	let timer = null
	return function() {
		clearTimeout(timer)
		timer = setTimeout(() => {
			func.apply(this, arguments)
		}, delay)
	}
}
function throttle(func, delay) {
	let timer = null
	return function() {
		if (!timer) {
			timer = setTimeout(() => {
				func.apply(this, arguments)
				timer = null
			}, delay)
		}
	}
}
```

#### 说一下vue的响应式原理
回答：
vue的双向数据绑定是进行数据劫持，然后通过发布订阅者模式实现的
vue2是通过Object.defineProperty()来进行数据劫持，而vue3是通过proxy来进行数据劫持
实现原理：
首先在创建vue实例的时候通过Observer函数对数据进行递归遍历，为每个数据添加上getter和setter属性，从而能够监听到数据的变化
然后通过Compile函数对vue的指令模版进行解析，将指令模版中的变量更改成数据，同时初始化渲染页面，同时为指令所在的节点的添加一个监听函数，当视图发生变化时从而更新数据。同时创建订阅者Watcher，通过Observe中的getter函数将订阅者添加进Dependency的订阅者数组，以便数据更新时通知订阅者，当数据发生变化时，触发Observer中的setter函数，从而触发Dependency中的notify函数对订阅者进行通知，订阅者触发对应的回调函数从而实现对视图的更新。

#### 对浏览器缓存的理解 （强缓存、协商缓存)
	304 Not Modified
	浏览器缓存相关
	HTTP 304状态码表示客户端发送了一个条件请求，但服务器确认客户端缓存的资源仍然有效并且未被修改。在这种情况下，服务器不会返回请求的资源，而是返回一个空的响应体和304状态码，告诉客户端可以使用缓存的资源。
		该状态码表示客户端发送附带条件的请求时，服务器端允许请求访问资源，但未满足条件的情况。
		304 状态码返回时，不包含任何响应的主体部分。304 虽然被划分在 3XX 类别中，但是和重定向没有关系。
		带条件的请求 (Http 条件请求) : 使用 Get方法 请求，请求报文中包含( `if-match` 、`if-none-match`  、`if-modified-since`、`if-unmodified-since` 、`if-range` ) 中任意首部。modified-since 、
		状态码304并不是一种错误，而是告诉客户端有缓存，直接使用缓存中的数据。返回页面的只有头部信息，是没有内容部分的，这样在一定程度上提高了网页的性能。

2. 小米：发现了代码质量的问题，在对应用商店B端项目进行开发的时候发现了一些可以优化的代码方面的问题，比如在项目运行的时候会报很多的eslint warning，提交代码的时候描述有部分不符合提交规范，前因就是项目是在开发前期没有重视代码质量问题，将配置时针对eslint的检查等级设为1。后续就针对这个问题跟导师进行提出和交流，在这个过程中输出了《代码规范可优化的方案》针对如何针对存量代码和增量代码规范问题进行校验。针对增量代码的处理，使用lint-staged，在git commit的时候通过lint-staged只针对缓存区内的代码文件进行校验，针对存量代码采取渐进式的方式进行修改，根据新需求的文件设计旧代码的改动，逐渐完善存量代码的规范，因为git hook都是本地的，不会随着git clone一起拷贝，就需要将这些钩子存储到实际的项目文件中，采取husky解决统一性的问题。配置pre-commit脚本触发lint- staged，针对提交规范的问题就采取commitlint后来了解到C端有一个正在用相关的工具，就考虑能不能将工具融入到b段中，就针对工具对源代码进行分析和修改，针对其中lint-staged与husky的问题进行修改。工具默认使用husky4.0以上版本。在husky@4中，`husky`在`package.json`中进行配置，husky会在`.git/hooks,` 写入所有的hooks脚本，里面的命令都是执行`husky.sh`。而husky.sh里面的脚本，就是获取你在`package.json`里面配置的`husky.hooks` 里面的键值对。如果当前脚本名和”键”对应上，就执行后续”值”的命令。所以每次的git操作，都会触发所有的`hook`脚本。这也导致了如果已经有了某个脚本，`husky`是不会覆盖掉的，也造成了部分代码库，在部分开发人员上好使，在部分开发人员上不好使的情况。而在Husky@7中采用的就是上述方案实现中一致性里的内容，修改`hooks`地址，在`.husky`文件中写入对应的钩子的脚本文件，在指定操作后触发对应的钩子从而执行脚本文件，比如使用`git commit` 触发`pre-commit`。而采用过高的版本包会导致与项目node版本产生冲突。在git 2.9之后，git 添加了一个配置功能，`core.hooksPath`, 可以指定hooks目录不在使用.git/hooks/。`husky install`命令 会创建.husky目录，并且执行 **`git config –local core.hooksPath .husky`**, 修改hooks目录。
