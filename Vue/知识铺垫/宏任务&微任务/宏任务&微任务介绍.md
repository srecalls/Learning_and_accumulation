MutationObserver 是 JavaScript 提供的一个 API，在浏览器环境下用于监听 DOM 树的变化，并在发生变化时执行相应的回调函数。它的主要用途是监视 DOM 的修改，以便在 DOM 树发生变化时做出相应的反应或执行特定的操作。

MutationObserver 提供了一种更高效且灵活的方式来观察 DOM 的变化，相比于之前的方式（如使用 DOM 事件或轮询），它具有以下优点：

1. 高性能：MutationObserver 采用异步机制，它会将 DOM 的变化捕获并放入一个队列中，然后一次性执行回调函数。这样可以减少不必要的回调次数，提高性能。

2. 监听多种变化：MutationObserver 可以监听几乎所有 DOM 的变化，包括节点的添加、删除、属性的修改、文本内容的改变等。它提供了一系列的配置选项，可以选择性地监听特定类型的变化。

3. 跨层级监听：MutationObserver 可以跨越 DOM 树的层级进行监听，即使是在嵌套的子元素中发生的变化，也可以被正确地捕获和处理。

4. 实时性：MutationObserver 可以实时地监听 DOM 的变化，并在变化发生时立即执行回调函数。这对于需要及时响应 DOM 变化的场景非常有用，如自动保存表单数据或实时更新页面内容。

使用 MutationObserver 的基本流程如下：

1. 创建一个 MutationObserver 实例，传入一个回调函数作为参数。

```javascript
const observer = new MutationObserver((mutations) => {
  // DOM 变化发生时执行的回调函数
});
```

2. 调用 MutationObserver 的 `observe()` 方法，传入要观察的目标节点和配置选项。

```javascript
const targetNode = document.getElementById("target");
const config = { attributes: true, childList: true, subtree: true };
observer.observe(targetNode, config);
```

3. 当目标节点或其子节点发生变化时，MutationObserver 会调用回调函数，并将变化的信息作为参数传递给回调函数。

```javascript
const observer = new MutationObserver((mutations) => {
  mutations.forEach((mutation) => {
    console.log(mutation.type); // 输出变化的类型
    console.log(mutation.target); // 输出发生变化的节点
    // 处理变化的操作
  });
});
```

4. 当不再需要监听变化时，可以调用 MutationObserver 的 `disconnect()` 方法停止观察。

```javascript
observer.disconnect();
```

总结来说，MutationObserver 提供了一种强大的机制来监听 DOM 的变化，并在变化发生时执行相应的操作。它在开发中可以用于实现一些高级的 DOM 监听和自动化处理的功能，如动态加载内容、实时更新等。
#### 1.只有状态变化才会进入微任务队列
当`Promise`对象的状态发生变化（从`pending`变为`fulfilled`或`rejected`）时，`.then()`方法将会被加入到微任务队列中，而不是其中的回调函数。只有当微任务队列中的所有任务执行完毕后，`.then()`方法中的回调函数才会被执行。

换句话说，当`Promise`对象状态变为`fulfilled`或`rejected`时，`.then()`方法本身会立即进入微任务队列，然后等待执行。一旦当前的JavaScript代码执行完毕，JavaScript引擎将检查微任务队列并按顺序执行其中的任务，包括`.then()`方法中的回调函数。其他任务的影响，具体取决于执行环境和任务队列的实现方式。


## 任务入队？

这里还有一个知识点，就是关于任务入队。

任务进入任务队列，其实会利用到浏览器的其他线程。虽然说`JavaScript`是单线程语言，但是浏览器不是单线程的。而不同的线程就会对不同的事件进行处理，当对应事件可以执行的时候，对应线程就会将其放入任务队列。

- js引擎线程：用于解释执行js代码、用户输入、网络请求等；
- GUI渲染线程：绘制用户界面，与JS主线程互斥（因为js可以操作DOM，进而会影响到GUI的渲染结果）；
- http异步网络请求线程：处理用户的get、post等请求，等返回结果后将回调函数推入到任务队列；
- 定时触发器线程：`setInterval`、`setTimeout`等待时间结束后，会把执行函数推入任务队列中；
- 浏览器事件处理线程：将`click`、`mouse`等UI交互事件发生后，将要执行的回调函数放入到事件队列中。

## **事件循环 Event Loop**？

其实宏任务队列和微任务队列的执行，就是事件循环的一部分了，所以放在这里一起说。

事件循环的具体流程如下：

1. 从宏任务队列中，按照**入队顺序**，找到第一个执行的宏任务，放入调用栈，开始执行；
2. 执行完**该宏任务**下所有同步任务后，即调用栈清空后，该宏任务被推出宏任务队列，然后微任务队列开始按照入队顺序，依次执行其中的微任务，**直至微任务队列清空为止**；
3. 当微任务队列清空后，一个事件循环结束；
4. 接着从宏任务队列中，找到下一个执行的宏任务，开始第二个事件循环，直至宏任务队列清空为止。
这里有几个重点：

- 当我们第一次执行的时候，解释器会将整体代码`script`放入宏任务队列中，因此事件循环是从第一个宏任务开始的；
- 如果在执行微任务的过程中，产生新的微任务添加到微任务队列中，也需要一起清空；微任务队列没清空之前，是不会执行下一个宏任务的。

## 调用顺序
在执行完同步任务以后也就是清空调用栈以后
首先会执行微任务队列的任务，把微任务队列的任务清空以后才会去执行宏任务

## async/await

`async/await` 所生成的代码属于微任务（microtask）。

在 JavaScript 中，任务（task）分为宏任务（macrotask）和微任务（microtask）两种类型。宏任务包括以下几种：

- script（整体代码）
- setTimeout
- setInterval
- setImmediate（Node.js 环境）
- I/O 操作（Node.js 环境）
- UI 渲染（浏览器环境）

而微任务包括以下几种：

- Promise.then()
- Promise.catch()
- Promise.finally()
- process.nextTick（Node.js 环境）
- MutationObserver（浏览器环境）

`async/await` 实际上是基于 `Promise` 实现的，`async` 函数会返回一个 `Promise` 对象，并且 `await` 关键字会暂停当前函数的执行，等待 `Promise` 对象的状态发生变化。当 `Promise` 对象的状态变为 resolved（已完成）时，`await` 关键字会恢复当前函数的执行，并返回 `Promise` 对象的 resolved 值。


`async/await` 是基于 `Promise` 实现的语法糖，`await` 关键字会暂停当前函数的执行，并等待一个 `Promise` 对象的状态发生变化。**在 `await` 关键字之前，该函数所生成的代码都会先执行**，而 `await` 关键字之后的代码会被添加到 `Promise` 对象的回调函数中，并在该 `Promise` 对象的状态发生变化后执行。如果是reject会抛出一个未捕获的异常，导致`async`函数的执行停止，并且控制权会传递给调用栈中的下一个异常处理程序。

因此，`async/await` 所生成的代码实际上是基于 `Promise` 的微任务，它会在当前宏任务执行完毕后立即执行。这也就意味着，如果在一个 `async` 函数中使用 `await` 等待一个 `Promise` 对象的状态变化，那么在 `Promise` 对象的状态变化之前，该 `async` 函数所生成的代码都不会执行，而只会在当前宏任务执行完毕后立即执行。

例如，以下是一个使用 `async/await` 的示例：

```javascript
async function fetchData() {
  const response = await fetch('/api/data');
  const data = await response.json();
  console.log(data);  // 这个会在微任务队列中
}

fetchData();
console.log('fetchData is called');
```

在这个例子中，我们定义了一个名为 `fetchData` 的 `async` 函数，并在其中使用 `await` 关键字等待一个 `Promise` 对象的状态变化。在 `await` 关键字之前，该 `async` 函数所生成的代码都不会执行，而只会在 `Promise` 对象的状态变化后立即执行。因此，在上面的代码中，`console.log('fetchData is called')` 语句会先执行，而 `console.log(data)` 语句会在 `Promise` 对象的状态变化后执行。

在这个例子中，`fetchData()` 函数会异步地获取 `/api/data` 的数据，然后使用 `await` 关键字等待该操作完成。在 `await` 关键字之前，该 `async` 函数所生成的代码都不会执行，而只会在 `Promise` 对象的状态变化后立即执行。

因此，在上面的代码中，`fetchData()` 函数会被异步调用，然后立即返回，而 `console.log('fetchData is called')` 语句会先执行。当 `/api/data` 的数据获取完成后，`Promise` 对象的状态会变为 resolved，然后 `data` 变量会被赋值为解析后的 JSON 数据，最后 `console.log(data)` 语句会输出数据到控制台。由于这些操作是在微任务队列中执行的，因此它们会在当前宏任务执行完毕后立即执行。

因此，上面的代码的输出结果为：

```
fetchData is called
[api/data 的 JSON 数据]
```

需要注意的是，如果 `/api/data` 的数据获取失败或解析出错，那么 `Promise` 对象的状态会变为 rejected，这时可以通过在 `async/await` 中使用 `try/catch` 块来捕获错误并进行处理。例如：

```javascript
async function fetchData() {
  try {
    const response = await fetch('/api/data');
    const data = await response.json();
    console.log(data);
  } catch (error) {
    console.error(error);
  }
}

fetchData();
console.log('fetchData is called');
``` 

在这个例子中，我们使用 `try/catch` 块来捕获可能发生的错误，并在控制台输出错误信息。


`fetchData` 函数本身不会被添加到微任务队列中，因为它是一个普通的函数，不是一个 Promise 对象或者一个异步函数。它的调用也不会被添加到微任务队列中，而是立即执行。

在上面的代码中，当调用 `fetchData()` 函数时，会立即执行该函数中的代码，包括使用 `await` 等待异步操作完成的部分。当 `await` 等待的异步操作完成后，会生成一个 Promise 对象，并将该 Promise 对象的回调函数添加到微任务队列中，以便在当前宏任务执行完毕后立即执行。因此，`console.log(data)` 语句会在微任务队列中执行，而不是在 `fetchData` 函数中执行。

需要注意的是，虽然 `fetchData` 函数本身不是异步函数，但是它内部使用了异步操作，并使用了 `await` 等待异步操作完成。因此，它的执行也会受到异步操作的影响，会在异步操作完成后继续执行。



##   有async一定要await吗
不是所有的 `async` 函数都需要使用 `await` 关键字。`async` 函数是用来定义异步函数的语法糖，它本身并不会使函数变成异步函数，只是使函数返回一个 Promise 对象。

如果在 `async` 函数中没有使用 `await` 关键字，那么该函数会立即返回一个 resolved 状态的 Promise 对象，并立即执行后面的代码。这个过程不会涉及到异步操作，也不会添加微任务到微任务队列中，因此该函数的执行过程会和普通函数一样。

以下是一个没有使用 `await` 关键字的 `async` 函数的示例：

```javascript
async function myFunc() {
  console.log('Hello');
  return 42;
}

myFunc().then(result => {
  console.log(result);
});
```

在这个示例中，`myFunc()` 函数并没有使用 `await` 关键字，它会立即执行，并返回一个 resolved 状态的 Promise 对象。因此，`console.log('Hello')` 语句会立即执行，然后 `myFunc()` 函数会返回一个解析后的值 `42`。最后，我们使用 `then()` 方法来处理 Promise 对象的结果，并输出 `42` 到控制台。

需要注意的是，虽然没有使用 `await` 关键字，但是 `async` 函数内部仍然可以包含异步操作，例如网络请求、定时器等，这些异步操作会在 `Promise` 对象的状态发生变化后执行回调函数，并添加微任务到微任务队列中。如果需要等待异步操作完成后再执行后面的代码，就需要使用 `await` 关键字等待该异步操作的结果。

于`async2()`函数没有返回任何值，它会返回一个`Promise`对象，并且该`Promise`对象的状态是`fulfilled`，值为`undefined`。

因此，`async` 函数并不一定需要使用 `await` 关键字，这取决于具体的业务需求。如果函数中没有异步操作，或者不需要等待异步操作完成后再执行后面的代码，那么就可以不使用 `await` 关键字。


## 定义异步函数的方式
异步函数可以通过以下两种方式定义：

1. 使用 `async/await` 语法糖

使用 `async/await` 语法糖可以方便地定义异步函数。异步函数定义时需要在函数声明前加上 `async` 关键字。在函数内部可以使用 `await` 关键字等待异步操作的完成。

例如，以下是一个使用 `async/await` 定义的异步函数的示例：

```javascript
async function fetchData() {
  const response = await fetch('/api/data');
  const data = await response.json();
  return data;
}

fetchData().then(data => {
  console.log(data);
});
```

在这个示例中，`fetchData()` 函数是一个异步函数，它使用 `await` 关键字等待网络请求的完成。当网络请求完成后，该函数会返回解析后的 JSON 数据。我们使用 `then()` 方法处理该 Promise 对象的结果，并输出数据到控制台。

2. 返回 Promise 对象

除了使用 `async/await` 语法糖外，异步函数还可以返回一个 Promise 对象。在函数内部可以执行异步操作，并将异步操作的结果作为 Promise 对象的解析值返回。

例如，以下是一个使用返回 Promise 对象定义的异步函数的示例：

```javascript
function fetchData() {
  return fetch('/api/data')
    .then(response => response.json())
    .then(data => {
      return data;
    });
}

fetchData().then(data => {
  console.log(data);
});
```

在这个示例中，`fetchData()` 函数返回一个 Promise 对象，该 Promise 对象的解析值是网络请求返回的 JSON 数据。我们使用 `then()` 方法处理该 Promise 对象的结果，并输出数据到控制台。

需要注意的是，无论是使用 `async/await` 语法糖还是返回 Promise 对象，异步函数都是通过返回 Promise 对象来实现异步操作的。因此，异步函数的返回值始终是一个 Promise 对象。

## 问题
这是每个标签页中，主线程在一帧内负责的任务吗。不仅要执行代码，还要执行渲染任务（之前提到的生成绘制记录），这些只是依靠一个线程来实现的吗。

一般线程都是硬件吗，它相当于什么，他一个就能干这么多活吗。

如果宏任务在一帧内执行不了会怎么办，还有是不是所有宏任务微任务执行完了之后才会执行渲染任务和空闲任务这些
这是一组非常深刻且触及浏览器核心机制的问题！你已经敏锐地发现了**浏览器性能瓶颈的根源**。

让我们逐一拆解你的三个核心疑问：

---

### 1. 🤯 主线程真的“一个人”干这么多活吗？

**是的，你没看错。**

正如你上传的第一张图片 (`image_6e5ca1.png`) 所示，在短短的 **16.6ms**（为了达到 60FPS 的流畅度）内，**渲染进程的主线程 (Main Thread)** 必须完成以下所有事情：

1. **执行 JavaScript**（宏任务，如 `setTimeout` 回调、点击事件）。
    
2. **清空微任务**（如 `Promise.then`）。
    
3. **更新动画**（`requestAnimationFrame`）。
    
4. **重排/布局 (Reflow)**：计算元素位置。
    
5. **重绘 (Repaint)**：生成绘制指令。
    

为什么还要它做渲染任务（生成绘制记录）？

因为 JavaScript 可以操作 DOM 和 CSS。如果把“执行代码”和“计算布局”放在两个不同的线程里并发执行，就会出现线程安全问题（比如 JS 刚刚删除了一个节点，而渲染线程正好要画这个节点，程序就会崩溃）。为了安全和简单，浏览器选择了让主线程“独揽大权”。

---

### 2. 💻 线程是硬件吗？它相当于什么？

**线程不是硬件，它是软件概念。**

为了让你理解“它为什么能干这么多活”，我们可以用一个**工厂**的比喻：

- **CPU 核心（硬件）** = **车间里的工人**。他是真正干活的肉体，速度极快（每秒能做几十亿次动作）。
    
- **线程（软件）** = **流水线传送带（或者任务清单）**。
    

它是怎么工作的？

操作系统会把这个“流水线”（线程）分配给一个“工人”（CPU 核心）。

- 虽然主线程只有一条“流水线”，但因为 CPU 这个“工人”动作快到离谱（纳秒级），他在 16.6ms（毫秒级）内，完全有时间先处理完 JS 代码，再处理完布局，再处理完绘制指令。
    
- 对于 CPU 来说，16ms 是一段非常漫长的时间。
    

它为什么能干这么多？

不是它想干这么多，而是它被迫干这么多。一旦 JS 代码写得太烂（比如写了个死循环，或者计算量太大），占用了 CPU 太久，CPU 就没时间去处理后面的“布局”和“绘制”了。

---

### 3. 🐢 如果宏任务在 16.6ms 内执行不完会怎么办？

这是一个非常关键的问题。这种情况被称为 **“长任务 (Long Task)”**。

如果一个宏任务（比如一个复杂的 JS 计算）执行了 50ms：

1. **阻塞渲染：** 在这 50ms 内，主线程被 JS 霸占。
    
2. **错过帧：** 浏览器本来应该在第 16ms 的时候进行渲染（布局+绘制），但因为主线程没空，渲染任务被推迟。
    
3. **结果：** 这一帧的画面没有更新。用户看到的页面是**静止**的。
    
4. **现象：** 这就是我们常说的 **“掉帧”**、**“卡顿”** 或 **“页面假死”**。

### 4. 🔄 是所有宏任务执行完了之后，才会执行渲染任务吗？

**不是！这是一个非常常见的误区。**

事件循环 (Event Loop) 的机制是：

“执行一个宏任务 -> 清空所有微任务 -> 尝试渲染 -> 下一轮循环”

请注意：是 **一个** 宏任务，而不是“所有”。

流程如下：

1. **取出一个** 宏任务（例如一个 `setTimeout` 回调）执行。
    
2. 执行过程中如果产生了微任务（Promise），加入微任务队列。
    
3. 宏任务执行完毕。
    
4. **立即清空微任务队列**（必须全部执行完）。
    
5. **关键点：** 此时浏览器会判断“是否到了该渲染下一帧的时候？”
    
    - **如果是：** 执行渲染流水线（样式计算 -> 布局 -> 生成绘制记录）。
        
    - **如果不是**（比如上一次渲染才过去 2ms）：跳过渲染，直接去取下一个宏任务。
        
6. **requestIdleCallback**（空闲任务）：只有在上述所有步骤做完，且 16.6ms 还有剩余时间时，才会执行。
    

总结：

浏览器会尽力保证每执行完一个宏任务（和其微任务）后，就去检查一下要不要渲染。它不会傻傻地等所有宏任务（比如队列里积压了 100 个点击事件）都做完才去画画，那样页面早就卡死了。

### 💡 核心总结

1. **主线程是超人：** 它既管 JS 逻辑，又管页面排版，所以**不要在 JS 里做耗时操作**。
    
2. **超时就卡顿：** 如果 JS 执行超过 16ms，渲染就会被推迟，页面就会掉帧。
    
3. **循环机制：** 做完**一个**宏任务，就看看能不能渲染。这也是为什么我们将耗时的大任务拆分成多个小的 `setTimeout` 可以避免卡顿的原因（给了浏览器在中间插入渲染的机会）。

这是一个非常棒的追问！你正在从表面的代码逻辑深入到计算机系统的底层运行机制。

我们先解决代码层面的问题，再通过一个生动的比喻来解决“线程有没有实体”这个抽象的物理问题。

### 一、 普通的 JS 代码算宏任务吗？

**算，而且是第一个宏任务。**

- **脚本整体 (Script)**：当浏览器加载你的 HTML 并解析到 `<script>` 标签（或者引入的 `.js` 文件）时，它会将 **“执行这整个脚本”** 作为一个**宏任务**放入队列中。
    
- **启动引擎**：主线程取出的第一个任务，就是这个“脚本整体”。
    

所以，**不存在**“既不是宏任务也不是微任务”的代码。

- **同步代码**：属于当前**正在执行的**那个任务（无论是宏还是微）的一部分，是任务的“具体内容”。
    
- **异步回调**：才会被拆分到后续的宏任务队列或微任务队列中。
    

#### 1. 宏任务 (Macro Task)

**概念**：由宿主环境（浏览器）发起的任务。它们通常比较“粗粒度”。 **常见例子**：

- **整体代码 script**（这是万恶之源，第一个）
    
- `setTimeout` / `setInterval`
    
- UI 交互事件（点击、滚动）
    
- I/O（网络请求回调）
    

#### 2. 微任务 (Micro Task)

**概念**：由 JavaScript 语言本身（JS 引擎）发起的任务。它们是为了在当前任务结束后、渲染之前，**插队**执行的“紧急任务”。 **常见例子**：

- `Promise.then` / `.catch` / `.finally`
    
- `MutationObserver` (监听 DOM 变化)
    
- `queueMicrotask`

### 二、 银行柜员比喻：彻底搞懂宏/微任务

想象你去**银行办业务**。

- **银行柜员** = **主线程** (一次只能接待一个人)。
    
- **排队的人** = **宏任务队列**。
    

#### 场景模拟：

1. **宏任务执行（普通的 JS 代码）**： 你（作为第一个宏任务）坐到了柜台前。你拿出一堆单子：存钱、取钱、查余额。这些是你的一行行**同步代码**，柜员会一口气给你办完，**中途不会停**。
    
2. **微任务产生（插队机制）**： 在你办业务的过程中，你突然对柜员说：“哎呀，我办完这些后，**立刻**还需要开个网银。”
    
    - 这叫 **微任务 (`Promise.then`)**。
        
    - 柜员不会让你去后面重新排队，而是说：“行，等你手头这堆事办完，**在叫下一个人之前**，我马上给你办开网银。”
        
3. **宏任务产生（重新排队）**： 你又说：“对了，我还需要买个理财产品，但我不急。”
    
    - 这叫 **宏任务 (`setTimeout`)**。
        
    - 柜员会给你一个号码牌，说：“这个得去后面**重新排队**（进入宏任务队列），等前面排队的人（其他宏任务）都办完了，再轮到你。”
        

**总结执行顺序：** 你手头的同步代码（当前宏任务） -> 你临时加急的业务（清空微任务） -> **（银行关门清算 = 渲染界面）** -> 叫下一个人（下一个宏任务）。
